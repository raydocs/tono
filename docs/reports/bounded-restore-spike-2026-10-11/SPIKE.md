## 0. 证据分级、术语与结论规则

| 级别 | 含义 | 能支撑什么 |
|---|---|---|
| **D** 文档保证 | Apple/Microsoft 公开文档或 man page 明确写出的语义 | 可作为设计依据；仍需在目标系统版本上实测一次 |
| **S** 源码依据 | Apple 开源代码（标明版本，例如 `configd-1405.100.8`）或 Tono 源码（标明 SHA） | 只说明实现方式，不保证目标机器上运行的就是这个版本，也不保证以后不变 |
| **O** 实测观察 | 本实验在指定系统版本、指定次数、指定时序覆盖下的结果 | **只代表“在这些条件下没有观察到反例”**，不是普遍上界，也不证明终态 |
| **U** 未证明 | 以上都支撑不了 | 设计必须按“可能不成立”处理，产品对外报“未知” |

三个状态必须分开，不能互相推出：
- **子进程已消失（child gone）**：我们拿到的进程句柄或 kqueue 确认进程已退出。这**不能**说明它交给系统的操作已经结束。
- **系统操作已终结（OS effect terminal）**：有 D 或 S 依据表明该通道上不会再有迟到生效（例如事务已中止，或已提交且后端不会排队重放）。没有依据就是 U。
- **分项已干净（component clean）**：按该分项所有相关层读回，都与目标值一致（例如 DNS 要同时看存储值、Setup、State 和实际解析器）。

结论规则：
1. 次数再多也只是 O。报告只能写“N 次、这些时序、没有观察到反例”，不能写“已证明”或“全部通过”。
2. 只有 O 而没有 D/S 的通道，其“终态”一律记为 U；对应分项能否显示“已恢复”由所有者决定（§8），本实验不替所有者作出这个决定。
3. 每次运行都要留存：脚本 SHA、OS 版本与构建号、机器标识（脱敏后）、基线、按时间排序的原始证据、查询失败记录、样本数、未测试的分支。

## 1. 执行安全门（E-F1）

### G0　恢复资格演练（任何故障注入之前必须通过）
每台被测设备（下称 DUT）逐项满足以下条件，留存证据，并由所有者在 PR 上确认：
1. **具名、可废弃**：写明设备或 VM 名称、OS 版本与构建号、CPU 架构；写明它是专用测试机，不是所有者日常使用的机器。
2. **权限确认**：Mac 需要 root（sudo），且允许修改 PF、DNS、launchd；Windows 需要提升后的 Administrator，且允许修改 WFP、DNS、SCM、计划任务。在 DUT 上实际执行一次只读命令和一次可逆的写命令来确认。
3. **带外控制**：要有一条不经过 DUT 自身网络的控制路径，例如虚拟化宿主机或云厂商的控制台、电源和快照回滚，或者物理机旁边有人操作。**经 DUT 网络的 Remote Control、SSH、远程桌面都不算带外控制。**
4. **离线回滚演练**：先在 DUT 上故意断网（例如断开虚拟网卡），然后只用带外路径完成一次恢复：VM 回滚快照；物理机按 §1.2 的基线恢复，并且不依赖 DUT 的 DNS 或网络连接。演练要计时、留证据。
5. **云 VM（例如 Devin）只是候选**：只有拿到厂商对本账号权限的证据（root/UAC、SCM/WFP 操作、带外控制台和电源、整机回滚）并完成第 4 步演练后，才能使用。Mac 会话休眠只保留磁盘、不保留运行中的进程，因此“休眠后恢复”不能当作快照。

演练没通过、带外控制不可用，或任一次恢复失败，**都立即停止**，不做任何故障注入。

### 1.2　基线采集与恢复（每轮实验前后都做）
- **采集**：
  - DNS：每个服务或接口的 IPv4 和 IPv6 DNS，包括存储值、Setup、State 和实际解析器；Windows 还包括四个注册表值，以及 IP Helper 读到的值。
  - 路由表（IPv4 和 IPv6）。
  - 代理和 PAC：Mac 是每个服务的设置；Windows 是 WinINET/WinHTTP 设置和用户代理设置。
  - PF：全局规则和所有 anchor，或 WFP 的全部 provider、sublayer 和过滤器（含 identity、action、layer、conditions）。
  - launchd 覆盖库、SCM 服务配置（启动类型、恢复动作、`FailureActionsOnNonCrashFailures`）、计划任务定义。
  - Tono 意图文件和 target 记录（仅在授权使用真实 Tono 的 DUT 上采集）。
- **恢复**：每类状态都写出具体的恢复命令，恢复后再采集一次，与基线逐项比对。有差异就停止实验，在报告中记录。
- **物理机**：没有快照，只能按上面的基线恢复。物理机实验必须有人在机器旁，或者有经过验证的独立管理路径。

### 1.3　禁止事项
- 不 flush 全局 PF、不停用 BFE、不杀 configd/SCM/WMI/Task Scheduler 等系统组件、不影响宿主机网络、不按进程组大范围终止共享进程。
- 不使用生产账号、生产节点目录或生产更新通道。
- 只使用**封闭的测试命名空间**：测试用 PF anchor、测试用 WFP provider/sublayer GUID、测试服务或测试接口、测试用 launchd label 和服务名。负载有上限。
- 真实 Tono 的 label、安装包和更新路径，只在所有者明确授权的、可废弃的 DUT 上使用（M3、W1 的“真实组”）。

### 1.4　数据
原始快照、`log stream`、`fs_usage`、ETW 记录和配置导出都放在私有存储里。推到 GitHub 前去掉账号、主机名、MAC 地址、IP、令牌和个人数据，只保留时间戳、命令、退出码和状态读数。

## 2. 观测器与对照（E-F2）

### 2.1　参数化观测对象
`netwatch`（Mac）和 `netwatch.ps1`（Windows）的观测对象全部由参数给出，并写进每次运行的记录：PF anchor 名、WFP provider/sublayer GUID、服务 ID、接口 GUID、代理键。**观测的对象必须就是该实验改动的对象。**

### 2.2　三层观测
1. **事件层**：
   - Mac：SCDynamicStore 通知，订阅 Setup 和 State 的 DNS、代理键，以及 `State:/Network/Global/DNS`；监听 `notify` 的 `com.apple.system.SystemConfiguration.dns_configuration` 通知。
   - Windows：`NotifyIpInterfaceChange`、`NotifyRouteChange2`，以及 DNS 注册表键的 `RegNotifyChangeKeyValue`；WFP 用 `FwpmFilterSubscribeChanges0` 订阅测试 provider 的过滤器变化。
2. **轮询层**：
   - Mac：20 ms 读取测试 anchor 的规则；PF 没有变更事件，用轮询补上。
   - 其他对象：200 ms 完整读回。
   - 轮询间隔写进报告，作为能检测到的最短瞬态的下限。
3. **效果层**：在测试网段放一个受控探针目标，对它每 5 ms 发一个 UDP 包和一次 TCP 连接尝试，并用测试 DNS 服务器每 50 ms 解析一个测试域名。效果层直接看“被不被阻断”和“解析到哪里”。比轮询短的阻断瞬态，只要持续时间长于探测间隔，就能在这一层看到。

所有记录都带单调时钟时间戳；事件丢失、查询失败、轮询超时都单独记录，**不能当成“没有变化”**。

### 2.3　写入者自带时间标记
harness 写入者在调用前、调用后都向管道写入标记（`enter`、`return`，单调时钟时间）。每次运行记录这些时刻：`kill_sent`、`exit_confirmed`（kqueue `NOTE_EXIT` 或进程句柄 wait）、`restore_start`、`restore_return`、`readback_done`。

每次终止按标记归类：
- `before_enter`：在 `enter` 之前终止；
- `in_call`：有 `enter`、没有 `return`；
- `after_return`：在 `return` 之后终止；
- `ambiguous`：标记缺失，或时间顺序不一致。

ambiguous 必须如实报告，**不能**算进 `in_call`。“发出终止时已经在调用里”只能说明终止落在该区间，不能推出调用中的某个具体点；报告要写明这一点。

### 2.4　阴性对照（每类观测器在每台 DUT 上先跑一遍）
- **迟到写入者**：恢复完成后 5、50、500 ms，故意写回旧值，例如 DNS 改回 127.0.0.1，或重新加载测试阻断规则。
- **短瞬态**：加载阻断规则，10 ms 后撤销。
- **读回失败**：注入查询失败，例如让 pfctl 返回错误，或让 WFP 枚举超时。

观测器必须检测到这三种对照，或者在报告中写明它检测不到哪一种（覆盖限制）。没跑对照的观测结果不能用。

### 2.5　网络单调性（C1）
- **作用范围**：从一次解除开始，到下一次**被准入的**新 Connect 为止。新 Connect 之后有意重新上锁，不算失败。
- **判定**：在该范围内，每个分项都只能从“受保护或残留”变为“已恢复”，不能出现反向变化。适用分项见 §4。

## 3. 写入者清单（E-F3 前置交付）

在任何关于“排除写入者”的结论之前，先从源码整理出一份**写入权限清单**（S，标明 SHA）：两个平台上所有能启动、启用、重新创建或直接执行 Tono 写入者的代码路径，包括：
- launchd/SCM 的自动拉起；
- update executor、rollback 和 staged/backup 二进制；
- 恢复计划任务；
- 安装器、修复、卸载重装；
- 直接 exec；
- 不同 label 或服务名；
- 由系统代理进程（WmiPrvSE、Task Scheduler、SCM）代为执行的操作。

每条路径都归入下面两类之一：
- **所有者授权的手动操作**：所有者自己运行安装包重装。这类不在保证范围内，作为已声明的限制。
- **自动的特权操作**：以 root 或 LocalSystem 自动运行。这类**仍在保证范围内**，必须由实验覆盖，或者在方案中把它列为 U。

进程快照只是证据，不能证明写入者已全部排除。

## 4. 分项与通道清单（E-F4）

| 分项 | Mac 写入/恢复通道（S） | Windows 写入/恢复通道（S） | 读回层 |
|---|---|---|---|
| 阻断 | PF `tono.killswitch` anchor（pfctl） | WFP 持久过滤器（BFE 事务） | 规则或过滤器全文（identity、action、layer、conditions），不能只数个数；同时保留非 Tono 规则 |
| DNS（含 IPv6、TUN DNS） | SCPreferences Commit/Apply（`ProtectedDNSManager.swift`） | 保护写入走 `SetInterfaceDnsSettings`（`native_apply.rs:1-8`，**只用于写入**）；恢复走 IPv4 CIM `SetDNSServerSearchOrder`（PowerShell，由 WmiPrvSE 代为执行）、IPv6 `netsh`，以及四个注册表值（`engine.rs:820-845,1041-1064,1344-1384`；`engine_ops.rs:369-378`） | Mac：存储值、Setup、State、实际解析器；Windows：注册表、IP Helper、实际解析器。要覆盖 DHCP 和静态、IPv4 和 IPv6 |
| Core/TUN/路由 | sing-box 进程、utun、路由表 | sing-box（Job 内）、Wintun、路由表 | 进程已退出、接口不存在、路由与基线一致 |
| AI 层 | resolver 文件、sinkhole、blackhole 路由 | 对应的 AI hold 过滤器和路由 | 逐条读回 |
| 代理/PAC | 每个服务的 HTTP/HTTPS/SOCKS/PAC | WinINET/WinHTTP 和用户代理 | 与基线一致；第三方应用设置的值保持不变 |

- **连通性检查**：使用受控目标，不依赖任何账号或令牌：
  - 普通站点：测试网段的 HTTP 服务器，加一个公开的、无需登录的站点。
  - AI 类：先解析域名，再对已知地址做 TCP 连接；不登录任何服务。
- 每次失败都要区分原因：DNS 失败、缓存、DoH、对端服务本身故障。**单次 HTTP 成功或失败都不能作为分项证据。**
- 本轮暂不测试的通道要明确列出，从可行性结论中排除，对应分项的“整体恢复”声明保持未决。

## 5. Mac 实验

### M1　DNS 写入者死亡后有无迟到覆盖（持久 SCPreferences）
- **假设**：root 客户端的 Commit 在客户端进程里直接写临时文件并 rename（S：`configd-1405.100.8` `SCPCommit.c`）；Apply 发出 `SCDynamicStoreNotifyValue`（S：`SCPApply.c`），由 PreferencesMonitor 在 run loop 上异步更新 Setup，再由 IPMonitor 另外发布解析器配置（S：`prefsmon.c`、`dns-configuration.c`）。公开头文件把 Apply 描述为**请求**，把 Lock 描述为对偏好设置的独占访问，**不是下游完成屏障**（S/D：`SCPreferences.h`）。因此“后端已静止”仍是 U，本实验只观察，不能证明。
- **依赖它的结论**：PROPOSAL §9.1 的 Mac DNS 行。
- **步骤**：
  1. 测试服务（不是主网卡服务）上，`scw` 循环执行 Lock → 写入 → Commit → Apply → Unlock，带 §2.3 的标记。
  2. 交错序列：终止 → 确认退出 → 恢复（Commit+Apply）→ 观察迟到变化。终止时机覆盖 `before_enter`、`in_call`（Commit 中）、`after_return`（Commit 后、Apply 前），以及 Apply 中。
  3. 后端繁忙条件：同时让另一个测试服务持续 Commit/Apply，并触发一次网络变化（切换测试接口、DHCP 续租），在有界负载下进行。
  4. 读回：存储值、Setup、State、实际解析器（`scutil --dns` 和 `dns_configuration` 通知）都要读；每轮都检查 `plutil -lint`。
  5. 次数：先做先导轮（每个时机 30 次、观察 30 s），再做正式轮（每个时机 300 次、观察 120 s）。正式轮是否全部执行，按 §9 的停止规则决定。
- **判定**：只报告 O，即各时机的样本数、有没有出现回退、各层读回的分布。出现任何回退或文件损坏，就判定为反例。没有反例时，终态仍记为 U（见上面的源码依据），能否显示“已恢复”交给 §8。
- **不成立时**：Mac DNS 在写入者被强制终止后只能报“未知”，或者转用 M2 方案。

### M2　临时 DNS 值（写入者会话结束即撤销）
- **假设**：用 `SCDynamicStoreAddTemporaryValue` 写入的 State 值，在写入会话结束时由 configd 删除。
- **步骤**：
  1. 用独立服务 ID 写入 State DNS，以及让它生效所需的服务排序。用实际解析器确认是否生效，包括作用域解析器。
  2. 终止写入者，测量从确认退出到 State 键删除、再到解析器更新的时间分布（200 次）。
  3. 在网络变化、睡眠唤醒、重启三种情况下各测一次。
- **判定**：只报告时间分布（O）。**不写“删除有上界”**；如果文档里写了删除时限，就引用文档（D），否则上界记为 U。
- **仍为 U**：这种方式与产品 fail-closed 要求是否兼容，在本实验范围之外，需要另做设计。

### M3　`launchctl disable` 能否隔离写入者启动
- **假设**：被 disable 的 system 域服务不会被 KeepAlive、`bootstrap`、`kickstart` 或开机加载启动。
- **步骤**：
  - 模拟组：使用测试 label。
  - 真实组：仅在获授权的 DUT 上做，使用真实 label `com.raydocs.tono.core-helper` 和 `com.raydocs.tono.update-executor`。
  1. 已在运行的写入者：disable 之后，进程是否仍在运行（预期是），以及终止后会不会被拉起。
  2. 待启动的写入者：disable 与 KeepAlive 节流期内的待重启同时发生。
  3. 启动路径：逐一尝试 `bootstrap`、`kickstart -k`、`load`、`load -w`、`enable`，以及直接 exec 二进制（预期 disable 拦不住直接 exec），记录退出码和进程是否运行。
  4. 替代路径：使用别的 label 指向同一二进制、staged/backup 二进制、删除 plist 后重新创建、卸载后重装。
  5. 并发情况：在 disable 前后分别进行 repair、update、rollback、install。
  6. 重启。
  7. 运行当前版本以及之前至少 3 个已发布的安装包，用 `log stream` 和 `fs_usage` 记录它们是否执行 enable、`load -w`，或直接启动写入者。
  8. 隔离生效后，再做一次清点和读回。
- **判定**：每条路径单独给出结论，并标明证据级别和属于 §3 的哪一类。自动特权路径只要有一条能绕过，就判为不成立。
- **不成立时**：该路径必须改由新版代码在启动前检查 target；做不到的，在 released 期间对应分项报“未知”，并写入已知限制。

### M4　解除组件的拉起机制（launchd）
- **步骤**：使用测试 label，同一份 plist 同时配置 `Sockets` 和 `KeepAlive.PathState`。
  1. 标记存在时，分别测试正常退出、SIGKILL、启动即崩溃（崩溃循环），记录拉起间隔和节流。
  2. 标记存在时重启。
  3. 删除标记后，确认不再保活，但仍能被 socket 激活。
  4. 如果 Sockets 和 PathState 不能共存，改为两个 label。此时两者必须通过同一把 flock 实现**单一所有者准入**，并测试两个 label 同时被激活的情况。
- **判定**：只判定拉起机制本身。持久协议由 L1 检验。

### M5　PF：被终止的 pfctl 与迟到生效
- **步骤**：
  1. 在测试 anchor 上用一份大规则集（有上限）循环加载，按 §2.3 的方式终止。每次读回规则全文，并检查读取错误。
  2. 交错序列：终止 → 确认退出 → flush 测试 anchor → 观察迟到重现。用 §2.4 的迟到写入者作为对照，同时跑效果层探针。
  3. 检查非 Tono 规则和全局 PF 状态是否保持不变。
  4. 检查 Tono 是否修改 `/etc/pf.conf` 或开机 anchor（S）。仅在授权 DUT 上做：disable daemon 后重启，观察 anchor 状态（O）。
- **判定**：全有或全无只说明加载的原子性。“flush 之后不会迟到重现”记为 O；只有找到 pf ioctl 同步语义的源码或文档依据，才能升级为 S/D。“重启后一定干净”只写成“在这些条件下观察到干净”。

### M6　写入者进程覆盖
- **步骤**：在连接中、`/update/stage` 中、修复中、睡眠唤醒中，用稳定身份（pid + 启动时间 + 可执行路径 + 代码签名）持续记录进程树。观测期间同时有新进程在创建，以检验清点与派生之间的竞争。分别比较 `launchctl kill`、按 pgid 终止、按身份递归终止三种方法，并验证观测器和解除组件自身都没有被误杀。
- **判定**：每种方法在每个场景下留下哪些进程（O）。存在覆盖不到的写入者时，按 §3 处理。

### M7　安全边界（Mac）
见 §6.3 的共同清单，以及 Mac 专项：
- `SockPathMode`、`SockPathOwner`、`SockPathGroup` 实际生效；
- 用审计令牌（`LOCAL_PEERTOKEN`）而不是 PID 校验对端；
- 解除组件的二进制、目录和状态文件为 root:wheel、用户不可写；
- 对状态文件和请求文件做符号链接替换测试。

## 6. Windows 实验

### W1　服务 Disabled 与计划任务禁用能否隔离写入者启动
- **背景（S）**：安装器配置的恢复动作是 5/10/30 s 后重启、24 h 后重置计数，并开启了 `FailureActionsOnNonCrashFailures`（`install_service.rs:2688-2693`）。恢复计划任务名为 “Tono Update Recovery v1”（`update.rs:1222`）。
- **步骤**：与 M3 对应。
  1. 已在运行的服务、正在运行的计划任务、已在运行的更新 executor。
  2. 待启动的写入者（落在 SCM 恢复动作的延迟期内）。
  3. 逐一尝试 `sc start`、App 内部的启动路径，以及直接运行服务 exe。
  4. 删除服务后重建，或由更新、修复流程重建。
  5. SYSTEM 身份的自动写入者重新启用服务。
  6. 重启。
  7. 运行当前版本以及之前至少 3 个已发布安装包。
  8. 走自动更新路径。
  9. 隔离生效后，再做一次清点和读回。
- **判定**：与 M3 相同，按 §3 分类。

### W2　Job Object 覆盖
- **背景（S）**：
  - Core 是在 spawn 之后才加入 Job 的（`core/manager.rs:1276-1294`），因此 spawn 和加入之间有一个窗口。
  - DNS 辅助进程是挂起状态下先加入 Job、再恢复运行（`core/process.rs:418-469`）。
  - Microsoft 文档：kill-on-close 在 Job 的**最后一个**句柄关闭时生效，并且只作用于已关联到该 Job 的进程；带 breakaway 标志或由代理（broker）创建的进程可以不在 Job 内。
- **步骤**：
  1. 实际成员：用 `IsProcessInJob` 和 `QueryInformationJobObject` 读出 Job 的真实成员。
  2. 句柄生命周期：句柄被复制或继承后，关闭“最后一个句柄”是否真的发生。
  3. breakaway 与嵌套 Job。
  4. 加入 Job 失败的情况。
  5. spawn 和加入之间的竞争。
  6. 由代理创建的子进程（WmiPrvSE、Task Scheduler）。
  7. 清点进行中又创建了新进程。
- **判定**：`TerminateProcess` 返回不等于进程已退出，必须等到稳定的进程句柄变为 signaled。由代理代为执行的操作（例如 CIM 恢复由 WmiPrvSE 执行）不在我们的进程树里，这类操作的终态记为 U，除非另有依据。

### W3　WFP/BFE：终止与迟到生效
- **背景（D）**：`FwpmEngineClose0` 的文档说明，客户端进程终止时会话关闭，进行中的事务被中止。文档没有给出完成时间的上限。
- **步骤**：全部使用测试 provider/sublayer GUID，观测器监视的也是这些 GUID。
  1. 事务提交前终止。
  2. 提交过程中终止（大事务、有上限，按 §2.3 标记）。
  3. 提交完成后终止。
  4. 交错序列：终止 → 确认退出 → 按 provider 删除 → 观察是否迟到重现，在 BFE 繁忙（有上限的并发枚举）时进行。
  5. 读回完整的过滤器语义：identity、action、layer、conditions。
  6. 重启后，持久过滤器是否仍然存在。
- **判定**：第 1、2 步说明事务原子性（O，加 D 依据）。“删除后不会迟到重现”是 O，终态以 D 为依据，没有时间上限。查询失败一律记为“未知”。不暂停 BFE。

### W4　实际的 DNS 恢复通道
- **步骤**：
  1. 在测试接口上覆盖 DHCP 与静态、IPv4 与 IPv6 的组合，使用产品实际的恢复通道：IPv4 CIM（PowerShell → WmiPrvSE）、IPv6 netsh、四个注册表值。
  2. 在调用中和调用返回后分别终止 PowerShell 或 netsh，并让 WmiPrvSE 保持在执行中。
  3. 交错序列：终止 → 确认退出 → 由另一路恢复写入原值 → 观察是否迟到回退，并测试延迟的接口通知和重新应用。
  4. 同时读回注册表、IP Helper 和实际解析器。
- **判定**：只报告 O。WmiPrvSE 代为执行的操作，在我们的进程退出后是否还会落地，**记为 U**，除非找到 D 依据。

### W5　解除服务的拉起机制（SCM）
- **背景（D）**：是否触发恢复动作，取决于服务报告的 SERVICE_STOPPED 状态、退出码和 `SERVICE_FAILURE_ACTIONS_FLAG`，**而不是简单的“正常退出还是异常退出”**。
- **步骤**：在实际配置下，覆盖以下几种停止方式：
  1. 报告 SERVICE_STOPPED，退出码为 0；
  2. 报告 SERVICE_STOPPED，退出码非 0；
  3. 不报告 SERVICE_STOPPED 就退出；
  4. 进程被直接终止。

  另外：
  - 每种方式都测一次重启后的表现；
  - 比较开机继续解除的两种方式：(a) 自动启动、无事可做时立即退出；(b) 由计划任务拉起；
  - 崩溃循环持续 10 分钟，检查 C1。
- **判定**：只判定拉起机制本身，持久协议由 L2 检验。

### W6　安全边界（Windows）
见 §6.3 的共同清单，以及 Windows 专项：
- SDDL 只授予交互用户 `SERVICE_START`；用标准用户测试 stop、config、binPath、恢复动作都被拒绝；
- `ImagePath` 加了引号，二进制和目录的 ACL 正确；
- `StartService` 传入的参数被忽略；
- 命名管道设置了 `PIPE_REJECT_REMOTE_CLIENTS`，测试抢先创建同名管道；
- 对状态文件和请求文件做重解析点（reparse point）替换测试。

### 6.3　共同安全清单（E-F6）
1. **只有 START 权限只能唤醒服务**：一个无关的标准用户（Windows），或另一个本地用户（Mac）启动解除组件后，如果没有后续经过认证、绑定所有者的请求，那么：不写 pending 或 fence，不禁用任何服务，不改动网络。崩溃恢复只能处理**之前已认证**的持久 pending 请求。
2. **授权不能只看签名或 PID**。逐项测试以下情况都被拒绝：
   - 绑定的 UID/SID/会话不符；
   - 签名有效但产品不对（同团队的其他产品）；
   - 签名正确的 Tono，但运行在错误的用户下；
   - PID 复用（必须用审计令牌或进程句柄这类稳定身份）；
   - 抢先创建 socket 或管道；
   - 远程客户端；
   - 畸形、超大、慢速请求（受截止时间约束）；
   - 重放；
   - 篡改 root/LocalSystem 状态文件或请求文件（符号链接、重解析点、ACL）。
3. **子进程操作**：路径和参数都是封闭的、由 root/SYSTEM 控制。
4. **判定标准**：经过认证的用户本来就能传入允许的字段（请求 UUID、期望代数），这不算提权。提权指的是：未授权的用户产生了效果，或者能执行任意操作。
5. **harness 客户端**不需要通过生产授权器。授权器单独用正、负两类客户端测试。

## 7. 解除生命周期实验（E-F5）

L1（Mac）和 L2（Windows）用一个**协议原型 harness** 实现 PROPOSAL §10 的单一 v2 序列。原型只作用于测试对象，不是产品代码。逐个注入以下切点，每个切点都检查四件事：各分项如实报“未知”、恢复所有权是持久的、操作幂等、旧清理碰不到新准入的会话。

1. 在写 pending 之前或之后崩溃；在写 fence 之前或之后崩溃。
2. 父进程死亡后子进程仍存活；子进程在确认退出之前，父进程被重新拉起。
3. 请求未得到答复后重放；G → G+1 → G+2（中间夹一次新 Connect）之后，旧请求重放。
4. 连续多次点击 Restore；两个客户端同时请求；客户端重启后再请求。
5. 新 Connect 之前已经排队的迟到重试。
6. 故意让子进程或后端操作拖过答复截止时间（例如让测试 DNS 写入卡住）。答复必须按时给出且为“未知”；新 Connect 的处理遵循 §10 的规则；迟到的恢复在新 Connect 之后落地时，新会话的监督能检测到漂移并重新应用，用阴性对照验证这一点能被发现。
7. 每个客户端的截止时间与以下环节分开测试：激活、合并、认证与 socket I/O、持久化（含 fsync 卡住）、worker 崩溃、子进程回收卡住。看门狗不能保证一定按时被调度：答复超时只说明“没在期限内答复”，**不能证明 worker 或后端已经结束**。
8. 两个 label 的情况（如果 M4 退回到这个方案）：同时激活时只有一个所有者。

## 8. 结果如何影响架构（交由所有者决定的部分已标明）

| 结果 | 影响 |
|---|---|
| 某通道的终态只有 O、没有 D/S | 该分项在写入者被强制终止后能否显示“已恢复”，**由所有者决定**：选项是始终报“未知”，或者作为已声明的限制显示“已恢复（附说明）”。本实验不替所有者作出决定。 |
| M3/W1 有自动特权路径能绕过隔离 | 该路径必须先改由新代码在启动前检查 target；否则抢占式方案不成立，回到所有者决定（含 #1504 的 (c) 方案） |
| M4/W5/L 实验发现拉起不可靠或网络来回变化 | 去掉自动续跑，改为“未完成即报未知，需用户再次恢复或执行外部救援步骤” |
| M6/W2 有覆盖不到的写入者 | 该写入者涉及的分项报“未知”，或改由它自己在启动前检查 target |
| M7/W6/§6.3 发现提权入口 | 实现前必须修改设计 |
| 某通道本轮未测 | 从可行性结论中排除，整体恢复声明保持未决 |

## 9. 日程、设备分配与停止规则（E-M1）

| 阶段 | 内容 | 机器 | 估计 |
|---|---|---|---|
| P0 | G0 演练、基线脚本、观测器与阴性对照 | 每台 DUT | 每台约 0.5–1 天，取决于厂商控制台 |
| P1 先导 | 每个实验每个时机 30 次、观察 30 s | VM | M1 约 4 × 30 × 40 s ≈ 1.3 h；其他实验同量级 |
| P2 正式 | 每个时机 300 次、观察 120 s（只跑 P1 有意义的时机） | VM 顺序执行 | 按 130 s 一轮算：M1 ≈ 43 h，W4（4 种组合 × 2 个时机）≈ 87 h，M5、W3 各约 22–33 h；其余实验以机制测试为主，各约 0.5–1 天 |
| P3 物理复跑 | M1、M2、M3、M5、M6，W1、W2、W3、W4，L1、L2 中受网卡、Wi-Fi、DHCP、IPv6、睡眠影响的部分 | 物理 Mac、物理 Windows | 每台约 2–4 天，有人值守 |

- 同一台机器上，会互相干扰网络的实验不并行跑。
- 总计约为**每个平台 2–3 周机器时间**，可以多台 VM 并行压缩。v1 写的“1–2 天”不成立，已撤回。
- **停止规则**：
  - G0 未通过，或任一次基线恢复失败，立即停止。
  - 先导轮出现反例，该时机不再跑正式轮，直接记为反例。
  - 观测器没能检出阴性对照，修好观测器之前不跑正式轮。
  - 连续两次 VM 回滚失败，停止使用该 VM。

## 10. VM 与物理机的边界

- 原生 VM（不是容器）适合做以下几类前期验证：API 与事务语义、持久化与重启、进程覆盖、ACL。
- VM 替代不了物理机验收的内容：真实网卡、Wi-Fi、以太网、DHCP、IPv6 的变化，睡眠唤醒，解析器、路由、TUN、AI、代理的收敛过程，以及“恢复后立刻 Connect”。
- VM 快照不一定同时原子地保存磁盘、进程和内核状态。
- VM 里测得的最大延迟不能当作生产环境的截止时间。
