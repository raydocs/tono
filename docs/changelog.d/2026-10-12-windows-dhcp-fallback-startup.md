## 2026-10-12 · Windows 精确 DNS 恢复失败后，把仍指向 Tono 解析器的网卡重置为 DHCP，由重启后的 Service 兜底
- 归属：SHIP_PLAN §2 item 10；Windows Service（`apps/windows/service`，DNS 引擎与 WFP 紧急解除、启动恢复）。
- 来源：基线 main `57776e805`；分支 `claude/win-dhcp-fallback-startup`，PR #1605（草稿）；尚未合 main。取代已关闭的 PR #1590 的 Service 部分（App 侧重试已在 #1599）。
- 缺陷修复：非卸载的紧急解除（释放服务 `clean_up`，即「恢复正常网络」按钮；非阶梯的更新执行器恢复）在精确恢复的适配器证明失败后，WFP 已拆除，但仍指向 Tono 目标（198.18.0.2 / 回环）的网卡留在死掉的解析器上。关联发现：`WIN-NRPT-KEPT-AFTER-EMERGENCY-DISARM`。
- 为什么放弃 #1590 的做法：它想在释放工作线程 45 秒的清理里完成 DHCP 重置，七轮审查都卡在同一点——被放弃的精确恢复的 `spawn_blocking` 线程会无限期持有 DNS 引擎的单写者占用（`DNS_CALL_IN_FLIGHT`），任何在 45 秒内的等待/保底/重试算术都无法保证重置真的跑到。
- 新设计（两处，一个共享函数）：
  1. 共享函数 `dns::reset_redirected_adapters_to_automatic()`（`dns/uninstall.rs`）：持 `DNS_OPERATION`，读取候选网卡（快照里的 ∪ 活动的）、按地址族分别评估（注册表 + 有效解析列表；快照里用户自己的回环豁免）、只把读作 Tono 目标的地址族重置为自动（DHCP）、回读验证、保留快照文件、再 `restore_resolver_policy()`。引擎忙（占用被持有，错误带 `DNS_ENGINE_WEDGED_PREFIX`）时立刻返回该错误，不等待、不重试；有效 DNS / 离线注册表读取被拒绝同样原样返回忙（不折算成「未知」），策略恢复一步被拒时整次尝试也报忙，不被适配器一步的普通错误遮住；快照已退休（`snapshot_was_restored`）时只作 GUID 范围，不作为回环归属的证据，仅 198.18.0.2 仍算 Tono 的；持锁后 `PROTECTION_WANTED` 已为真则不动任何东西，返回带 `TONO_DNS_FALLBACK_SUPERSEDED` 的取代错误。
  2. 紧急解除（`windows_kill_switch/emergency.rs`，仅非阶梯分支）：顺序不变（恢复 → 墓碑 → AI 保留 → 拆 WFP → 后续 → 意图 → NRPT 清扫 → 结果）；调用方给了期限（释放工作线程，`emergency_disarm_windows_kill_switch_until`）时精确恢复限 10 秒，无期限仍是 `DNS_RESTORE_TIMEOUT` 40 秒；NRPT 清扫之后、DNS 结果为错误或超时时调用共享函数**一次**：成功/失败都只作为 `TONO_DNS_FALLBACK` 备注附在原错误后，引擎忙则记「推迟到主 Service 的启动恢复」；返回的仍是原错误，调用方不会把它读成「已恢复」。这一次尝试跑在紧急解除已持有的 `WFP_OPERATION` 之内（整个解除期间持锁不变），期间置位进行中标记 `DNS_FALLBACK_IN_PROGRESS`，整体期限 `DNS_FALLBACK_ATTEMPT_BUDGET` = 60 秒；不用 timeout 包住尝试本身（丢弃 future 不会停止阻塞写者）。
  3. 启动恢复（`windows_kill_switch/startup.rs`、`disarm.rs`）：释放工作线程清理后会重启主 Service（尝试，不是保证），这个新进程有干净的占用槽、没有清理期限。启动路径在精确恢复失败后**只登记请求**（`request_startup_dns_fallback()` 置位）：`restore_on_service_start` 的无意图（含残留 WFP、残留探测报错）、未要求意图分支，以及走通用释放的分支（不可用/损坏/不可读意图、启动释放重试循环里的通用释放）——通用释放 `release_general_traffic_requesting_dns_fallback` 记录 DNS 失败，在 WFP 拆除成功之后才登记请求；运行期释放（不健康会话）不登记。任务由 Service 二进制在 SCM 与独立两条路径里调用 `spawn_startup_dns_fallback_if_wanted()` 启动：位置在 `initialize_protected_dns_status`、两个看门狗、网络监视与启动 reconcile 之后、IPC 监督器开始服务之前，所以不会在 DNS 状态缓存初始化之前抢 `DNS_OPERATION`，启动路径本身不变长（任务晚于这些步骤才启动）。已越过这个启动点之后的请求（释放重试循环按定时器运行）直接启动任务。任务的循环上限 `STARTUP_DNS_FALLBACK_BOUND` = 90 秒，只在两次尝试之间检查；每次尝试只在开头短暂持有 `WFP_OPERATION`（先 WFP 后 DNS，与其它路径同序）：复查 `ARMED` 为空且 `PROTECTION_WANTED` 为假，置位进行中标记，随即释放 WFP；共享函数在持有 `DNS_OPERATION` 后再复查 `PROTECTION_WANTED`。重新布防（Connect）的围栏见第 2 轮续记：不再靠整次尝试持有 WFP 锁，而靠这个标记与引擎占用，Connect 被拒绝而不排队。成功则记录被重置的 GUID 并停止，引擎忙则 1 秒后重试，被取代（保护重新被要求）或其它错误记录后停止。要求意图（重新布防）的分支从不登记。
- 新增/优化：无。
- 工程与测试：全部为桩引擎测试（无需 Windows 设备）。新测试钩子：真实占用的持有者 `park_engine_call`（经 `bounded_dns_call` 超时后线程仍占着占用，沿用 `dns/tests.rs` 里 mpsc 通道的做法）、有效 DNS / 离线注册表状态、NRPT 清扫计数；桩引擎的读写在占用被持有时同样拒绝。回归：`dns/tests.rs` 的范围测试（有效列表仍为 Tono、已恢复的网卡不动、用户自己的回环不动、离线快照网卡、读回仍为 Tono 则不算成功、快照保留与策略恢复、引擎忙立即拒绝），`windows_kill_switch/tests.rs` 的 T2–T6（紧急解除空闲时重置一次且返回原错误加备注、占用被持有时 1 秒内拒绝且 NRPT 清扫照常、启动无意图/未要求意图在返回后由脱离任务重置、要求意图不 spawn、占用 2 秒类的释放后重试、永不释放则在边界停止——边界由注入参数缩短，不用全局除数）。

- 剩余限制：无实机验证（需确认「恢复正常网络」后系统解析走家宽 DNS）；重启主 Service 是尝试而非保证（SCM 重启持续失败则没有兜底）；释放工作线程的报告可能仍把 DNS 写成残留/读不出，因为兜底在报告之后由重启的 Service 完成；新进程里引擎本身若也卡住，兜底在 90 秒处停止（只在两次尝试之间检查），快照保留，下一次启动再试；单次尝试整体期限 60 秒、两次文件读取各 5 秒（合计约 70 秒），循环取得 WFP 锁之后最长约 160 秒（锁排队不计入；Connect 对 WFP 锁的等待另有 5 秒上限，见第 3 轮续记）；尝试进行中，以及被放弃的引擎写者仍持有占用期间（可无限期，引擎卡死时），Connect 不排队而是等待至多 5 秒后被拒绝（`TONO_NETWORK_RESTORE_IN_PROGRESS: a network restore is still writing DNS; retry in a few seconds`）；App 未改，该拒绝作为「启动 Windows kill switch 失败」的原文显示，用户稍后手动重试；`--emergency-disarm` 命令行与开始菜单入口走卸载阶梯，不经过此分支；`ensure_restored()==Ok` 在快照缺失/已退休等 registry-only 出口并非在所有情况下都是有效 DNS 的完整证明；并发的精确恢复与兜底之间的文件写入/删除没有跨进程围栏。
- 第 1 轮续记（Codex FAIL，五个 MAJOR，设计未被质疑）：M1 重新布防竞态——每次尝试在 `WFP_OPERATION` 之内，持锁后复查 `ARMED` 与 `PROTECTION_WANTED`；M2 退休快照——只作 GUID 范围；M3 其余启动分支——通用释放记录 DNS 失败并在 WFP 拆除后登记请求，残留探测抽成可测的 `residual_filters_at_startup`；M4 忙被吞——读取层与合并处原样保留忙；M5 IPC 就绪——启动路径只登记，任务在 Service 二进制的启动点启动。
- 第 2 轮续记（Codex FAIL，三个 MAJOR，设计未被质疑，业主批准最后一轮）：R2-F1 第 1 轮「整次尝试持有 WFP 锁」只围住了 async 等待者，没围住内部引擎调用超时后被放弃、仍在写注册表/网卡的阻塞线程——改为进行中标记 `DNS_FALLBACK_IN_PROGRESS`（启动尝试在 `WFP_OPERATION` 下检查并置位，随即释放；紧急解除在其已持有的 WFP 锁下置位，结束清除，RAII 保证任何结局都清除）加引擎占用 `dns::engine_claim_is_held()`，`arm_bootstrap_waiting`（`arm_bootstrap` 的 5 秒版）在 WFP 锁下检查两者，任一成立则放锁、每 100 毫秒轮询至多 5 秒，仍成立则以 `TONO_NETWORK_RESTORE_IN_PROGRESS` 拒绝；唯一的生产布防入口是 `core/server/handlers.rs` 的 StartClash，看门狗、`lock`/`mark_verified`/`replace_proxy_endpoints` 都要求已有 ARMED，不会从空布防，启动恢复只在启动点之前布防已要求的意图；R2-F2 尝试没有时限——快照与退休记录两次文件读取各 `DNS_FALLBACK_FILE_READ_TIMEOUT` = 5 秒（普通错误，循环停止），整次尝试 `DNS_FALLBACK_ATTEMPT_BUDGET` = 60 秒的累计期限经任务局部量传给每个引擎调用（`bounded_dns_call` 取自身预算与剩余时间的较小者，剩余为零则不再发起并返回 `TONO_DNS_FALLBACK_ATTEMPT_TIMEOUT`，按忙重试），DNS 锁等待同样受期限约束；超时的内部调用仍按原样被放弃并持有占用，由上述围栏挡住 Connect；R2-F3 启动 reconcile 的未验证屏障退休（`retire_unverified_on_service_start`）在精确恢复失败后释放通用流量却不登记请求——改用登记版释放（WFP 拆除成功后登记），运行期不健康会话释放仍不登记；desired-Core 恢复被跳过后 `bin/service.rs` 仍会走到启动点。第 1 轮两个测试之一（「Connect 排在尝试之后」）断言的前提已被取代，改为断言标记围栏。
- 第 3 轮续记（Codex FAIL，两个 MAJOR 两个 MINOR，设计未被质疑，业主批准再一轮）：R3-F1 启动退休的精确恢复失败且其自身 WFP 拆除也失败时，请求在包装函数里没登记就返回，之后看门狗核心窗口经 `release_unproven_wanted_session_unlocked` 重试成功拆除，却不登记——新增状态 `STARTUP_RETIREMENT_OWES_DNS_FALLBACK`（`state.rs`）：`retire_unverified_on_service_start` 在调用登记版释放前置位，包装函数成功返回后清除；重试路径记录自己的 DNS 恢复是否失败，WFP 拆除成功后消费该状态，仅当状态已置位且恢复失败时才登记请求（恢复证明则只清除）；新的 Connect 布防也清除它；运行期不健康会话释放不看该状态，仍不登记。R3-F2 尝试期限错误 `TONO_DNS_FALLBACK_ATTEMPT_TIMEOUT` 在有效 DNS 读取与离线注册表读取处被降为「未知」/普通错误，策略腿合并处只保留忙——新增 `is_fallback_retryable`（忙或期限，`dns/uninstall.rs`）用于两处读取、重置腿提前返回和两腿合并，循环原先已把期限错误当作忙重试。MINOR：Connect 对 WFP 锁的获取现在同受 `ARM_FENCE_WAIT`（5 秒）限制，到期以同一前缀拒绝（`StartClash` 对该前缀的处理不变），所以 5 秒是含锁排队的完整等待上限；尝试自身的 160 秒数字仍是取得 WFP 锁之后的预算；新测试用 `FallbackFixture`（`Drop`）清理标记、欠债状态、兜底钩子与桩适配器，断言失败不再污染后续测试。已知局限：离线注册表读取处的回归测试与有效读取处同样得到期限错误，不能单独区分这两处。
