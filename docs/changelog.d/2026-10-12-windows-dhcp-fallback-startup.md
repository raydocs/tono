## 2026-10-12 · Windows 精确 DNS 恢复失败后，把仍指向 Tono 解析器的网卡重置为 DHCP，由重启后的 Service 兜底
- 归属：SHIP_PLAN §2 item 10；Windows Service（`apps/windows/service`，DNS 引擎与 WFP 紧急解除、启动恢复）。
- 来源：基线 main `57776e805`；分支 `claude/win-dhcp-fallback-startup`，PR #1605（草稿）；尚未合 main。取代已关闭的 PR #1590 的 Service 部分（App 侧重试已在 #1599）。
- 缺陷修复：非卸载的紧急解除（释放服务 `clean_up`，即「恢复正常网络」按钮；非阶梯的更新执行器恢复）在精确恢复的适配器证明失败后，WFP 已拆除，但仍指向 Tono 目标（198.18.0.2 / 回环）的网卡留在死掉的解析器上。关联发现：`WIN-NRPT-KEPT-AFTER-EMERGENCY-DISARM`。
- 为什么放弃 #1590 的做法：它想在释放工作线程 45 秒的清理里完成 DHCP 重置，七轮审查都卡在同一点——被放弃的精确恢复的 `spawn_blocking` 线程会无限期持有 DNS 引擎的单写者占用（`DNS_CALL_IN_FLIGHT`），任何在 45 秒内的等待/保底/重试算术都无法保证重置真的跑到。
- 新设计（两处，一个共享函数）：
  1. 共享函数 `dns::reset_redirected_adapters_to_automatic()`（`dns/uninstall.rs`）：持 `DNS_OPERATION`，读取候选网卡（快照里的 ∪ 活动的）、按地址族分别评估（注册表 + 有效解析列表；快照里用户自己的回环豁免）、只把读作 Tono 目标的地址族重置为自动（DHCP）、回读验证、保留快照文件、再 `restore_resolver_policy()`。引擎忙（占用被持有，错误带 `DNS_ENGINE_WEDGED_PREFIX`）时立刻返回该错误，不等待、不重试；有效 DNS / 离线注册表读取被拒绝同样原样返回忙（不折算成「未知」），策略恢复一步被拒时整次尝试也报忙，不被适配器一步的普通错误遮住；快照已退休（`snapshot_was_restored`）时只作 GUID 范围，不作为回环归属的证据，仅 198.18.0.2 仍算 Tono 的；持锁后 `PROTECTION_WANTED` 已为真则不动任何东西，返回带 `TONO_DNS_FALLBACK_SUPERSEDED` 的取代错误。
  2. 紧急解除（`windows_kill_switch/emergency.rs`，仅非阶梯分支）：顺序不变（恢复 → 墓碑 → AI 保留 → 拆 WFP → 后续 → 意图 → NRPT 清扫 → 结果）；调用方给了期限（释放工作线程，`emergency_disarm_windows_kill_switch_until`）时精确恢复限 10 秒，无期限仍是 `DNS_RESTORE_TIMEOUT` 40 秒；NRPT 清扫之后、DNS 结果为错误或超时时调用共享函数**一次**：成功/失败都只作为 `TONO_DNS_FALLBACK` 备注附在原错误后，引擎忙则记「推迟到主 Service 的启动恢复」；返回的仍是原错误，调用方不会把它读成「已恢复」。这一次尝试跑在紧急解除已持有的 `WFP_OPERATION` 之内，不再用 timeout 包住（内部每个引擎调用自带上限，引擎被占用时立即拒绝）。
  3. 启动恢复（`windows_kill_switch/startup.rs`、`disarm.rs`）：释放工作线程清理后会重启主 Service（尝试，不是保证），这个新进程有干净的占用槽、没有清理期限。启动路径在精确恢复失败后**只登记请求**（`request_startup_dns_fallback()` 置位）：`restore_on_service_start` 的无意图（含残留 WFP、残留探测报错）、未要求意图分支，以及走通用释放的分支（不可用/损坏/不可读意图、启动释放重试循环里的通用释放）——通用释放 `release_general_traffic_requesting_dns_fallback` 记录 DNS 失败，在 WFP 拆除成功之后才登记请求；运行期释放（不健康会话）不登记。任务由 Service 二进制在 SCM 与独立两条路径里调用 `spawn_startup_dns_fallback_if_wanted()` 启动：位置在 `initialize_protected_dns_status`、两个看门狗、网络监视与启动 reconcile 之后、IPC 监督器开始服务之前，所以不会在 DNS 状态缓存初始化之前抢 `DNS_OPERATION`，启动路径本身不变长（任务晚于这些步骤才启动）。已越过这个启动点之后的请求（释放重试循环按定时器运行）直接启动任务。任务最多 `STARTUP_DNS_FALLBACK_BOUND` = 90 秒，**每次尝试整体持有 `WFP_OPERATION`**（先 WFP 后 DNS，与其它路径同序），持锁后复查 `ARMED`，共享函数在持有 `DNS_OPERATION` 后复查 `PROTECTION_WANTED`：重新布防的 Connect 要么在尝试之前（任务看到后停止），要么排在整次尝试之后，不会在中途布防；90 秒只在两次尝试之间检查，不用 timeout 包住尝试（丢弃 future 不会停止阻塞写者）。成功则记录被重置的 GUID 并停止，引擎忙则 1 秒后重试，被取代（保护重新被要求）或其它错误记录后停止。要求意图（重新布防）的分支从不登记。
- 新增/优化：无。
- 工程与测试：全部为桩引擎测试（无需 Windows 设备）。新测试钩子：真实占用的持有者 `park_engine_call`（经 `bounded_dns_call` 超时后线程仍占着占用，沿用 `dns/tests.rs` 里 mpsc 通道的做法）、有效 DNS / 离线注册表状态、NRPT 清扫计数；桩引擎的读写在占用被持有时同样拒绝。回归：`dns/tests.rs` 的范围测试（有效列表仍为 Tono、已恢复的网卡不动、用户自己的回环不动、离线快照网卡、读回仍为 Tono 则不算成功、快照保留与策略恢复、引擎忙立即拒绝），`windows_kill_switch/tests.rs` 的 T2–T6（紧急解除空闲时重置一次且返回原错误加备注、占用被持有时 1 秒内拒绝且 NRPT 清扫照常、启动无意图/未要求意图在返回后由脱离任务重置、要求意图不 spawn、占用 2 秒类的释放后重试、永不释放则在边界停止——边界由注入参数缩短，不用全局除数）。

- 剩余限制：无实机验证（需确认「恢复正常网络」后系统解析走家宽 DNS）；重启主 Service 是尝试而非保证（SCM 重启持续失败则没有兜底）；释放工作线程的报告可能仍把 DNS 写成残留/读不出，因为兜底在报告之后由重启的 Service 完成；新进程里引擎本身若也卡住，兜底在 90 秒处停止（只在两次尝试之间检查），快照保留，下一次启动再试；一次尝试内的引擎调用各自有上限，尝试期间持有 `WFP_OPERATION`，会让同时到来的 Connect 排在其后；`--emergency-disarm` 命令行与开始菜单入口走卸载阶梯，不经过此分支；`ensure_restored()==Ok` 在快照缺失/已退休等 registry-only 出口并非在所有情况下都是有效 DNS 的完整证明；并发的精确恢复与兜底之间的文件写入/删除没有跨进程围栏。
