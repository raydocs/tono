## 2026-10-12 · Mac PF：每份规则集都放行 DHCP 与邻居发现（换 Wi‑Fi 后无法上网）
- 归属：SHIP_PLAN §2 item 10「连不上且无下一手」；macOS helper。
- 来源：基线 `fd438f627` → 分支 `claude/wifi-switch-mac-pf-dhcp`，PR #1591（草稿，未合 main）。
- 缺陷修复：旧版 `renderRules` 只在有隧道（`tunnelInterfaces` 非空）时才写 `tono-dhcp`（255.255.255.255:67 广播 DHCP）和 `tono-ndp`（IPv6 邻居发现，icmp6 133–137）。每一份无隧道规则集（连接开始的 bootstrap、换网络时的 preserve 拆除、`reassertIfNeeded`、helper 的紧急阻断）因此以 `block drop out quick all` 收尾，没有 DHCP/NDP 放行。换 Wi‑Fi（手机热点到酒店/办公室）后 Mac 正处于这种状态，可能拿不到新网络的租约，`NetworkUplinkSnapshot.classify` 只读到 `.inconclusive`，不触发 `.moved` 重连，用户只能卸载 Tono 才能上网。改后：这两组放行出现在 `renderRules` 产生的每一份规则集里，无隧道时的 DHCP 放行文本不变，NDP 放行改为 `no state`（见续记）。两组放行都在最终 `block drop out quick all` 之前；在有隧道的规则集里它们的位置不变，仍排在物理接口 DNS 阻断之后，无隧道规则集没有这些 DNS 阻断。有隧道的规则集逐字节不变。
- DNS 不外泄（所有者约束）：新增放行只有 UDP 68→255.255.255.255:67、67→68 和 icmp6 133–137，没有任何 53/853 的 `pass`；无隧道规则集里 DNS 照旧由最终 `block drop out quick all` 拦住。新自测断言无隧道规则集没有 53/853 的 `pass` 行，并断言有隧道时物理接口 DNS 阻断（`tono-lan-dns`，`on { en0 } … port { 53, 853 }`）仍在。注意：该 DNS 阻断本来就只在有隧道时渲染，无隧道规则集本来就没有它，靠最终 block 兜底，本次不改。系统解析器方面：helper 的 `ProtectedDNSManager.scSetDNS`（`ProtectedDNSManager.swift` 1079–1105）把 `127.0.0.1` 写进该网络服务 Setup 的 DNS `ServerAddresses`（1099 行，1102–1103 行提交并应用）；Setup 里的显式列表优先于 DHCP 租约给的 DNS（configd 行为，未在真机验证），所以换网络后拿到的租约改变不了这台 Mac 用哪个解析器。这个钉住在连接成功后由 `enableProtectedDNS`（`AppState+Connect.swift` 446）写入；换网络的 preserve 拆除不会恢复 DNS（`restoreDNS` 只在 `releaseKillSwitch` 时调用，1187–1203 行），所以 preserve 窗口里解析器仍是 127.0.0.1（Core 已停，查询失败而不是外泄）。新连接刚开始的 bootstrap 窗口里钉住尚未写入，系统解析器可能是租约给的 DNS，此时防止泄漏的是 PF（无 53/853 放行），不是这个钉住。
- 新增/优化：与 Windows `intent_floor` 对齐的方式是：每个武装模式都有基础设施例外（Windows 还放行有界的 DHCPv4 单播续租和 DHCPv6，见 `wfp_model.rs` 250–303、348–364 行；本次 Mac 只加广播 DHCPv4 和 NDP，不是同一份放行集合）；范围和理由见决策 097。mDNS、IGMP、Continuity 仍只在有隧道时渲染，不受“允许本地网络设备”开关控制；`tono-lan`、link-local、multicast、SSDP 仍只在有隧道时渲染，且受该开关控制。均没有改动。
- 工程与测试：新增一条 helper 自测 `runNoTunnelDHCPNDPSelfTest`（无隧道规则集渲染两条 `tono-dhcp` 与两条 `tono-ndp`，且都在最终 block 之前）。更新两条原来断言“无隧道时没有 DHCP/NDP”的旧断言：`tunnelOnlyLabels`（boot restore 无隧道形态）不再含 `tono-dhcp`/`tono-ndp`，`emergencyExpected`（紧急规则集整串比较）加入这四行。Helper 版本 4.52.51 → 4.52.52（续记中再升到 4.52.53），`CONTRACT.sha256` 重新计算（构建门要求：PF 渲染变了必须升版，否则已安装的旧 daemon 永远不会更新）。协议（IPC）本身未变。

- 续记 2026-10-12 · Codex 审查第 1 轮（头 `1cb2c6469`，结论 FAIL：1 主要、1 次要）：
  - F1（主要）：无隧道规则集里两条 `tono-ndp` 都是 `keep state (if-bound)`。Apple PF 对非错误 ICMPv6 的状态键是地址加 icmp6 id、不含类型，且先查状态后匹配规则，LAN 上的对端可用伪造的公网 IPv6 源地址和选定 id 发 type 134（RA）建立状态，之后本机任何非特权进程的 type 128（Echo Request）可借该状态在 bootstrap/紧急模式下从隧道外发出载荷。处理：无隧道时两个方向都改 `no state`（各方向本来就有独立放行，不需要返回状态）；有隧道的 `tono-ndp` 保持原有 `keep state (if-bound)`，字节不变（该处既有行为，不在本次范围）。自测加断言：无隧道的两条 NDP 都含 `no state` 且不含 `keep state`；`emergencyExpected` 的 NDP 两行相应改为 `no state`。Helper 版本升到 4.52.53（构建门要求：源码变而版本不变会被拒绝），`CONTRACT.sha256` 重新计算。
  - F2（次要）：文档事实更正。(a) 有隧道时 DHCP/NDP 排在物理接口 DNS 阻断之后；(b) Windows 地板还放行 DHCPv4 单播续租和 DHCPv6，对齐说法改为“每个武装模式都有基础设施例外”，并删去“再加这些会超过 Windows”的说法；(c) mDNS/IGMP/Continuity 受隧道门控但不受“允许本地网络设备”控制，LAN/link-local/multicast/SSDP 才受该开关控制。已在本条目与决策 097 更正。
  - 验证：本轮红提交 `116b5aee4`（只改期望与自测并升版）与绿提交各由 `ci-gate` 判定，结果记在 PR #1591 正文「Codex review round 1」。未执行：真机测试。
  - F1 的连带修正（CI 暴露）：无隧道的 `no state` NDP 放行在 bootstrap → 隧道 arm 时被算作“撤销”，`withdrawnHosts` 认不出它的形状，于是每次隧道 arm 都退化成整机状态清空（`control relay self-test failed: tunnel-arm-kills-relay-states, exit-on-a-relay-node-is-spared`）。`stateDisposal` 现在不把 `no state` 的放行算作撤销（不留状态的规则被撤销时无状态可杀）；有状态的撤销判断不变。自测加断言：仅撤销无状态 NDP 放行为 `.keep`。这是 `stateDisposal` 语义的一处收窄，需要审查者看一眼。
