## 2026-10-13 · A pasted home line with a different password, and an operator onboarding with a pasted line
- Status: provisional (the owner may overturn it; only the owner sets `owner` or `reversed`)
- Chosen: (1) `POST home-exits/assign` (and onboarding, which calls it) refuses a pasted line whose host, port and username match a stored home but whose password differs from the stored one, with `409 HOME_PASSWORD_DIFFERS`, unless that line is flagged for rotation (then the pasted password is the rotation, as before). Nothing is overwritten and nothing is dropped silently; the operator updates the home exit on purpose (`PATCH home-exits/{id}`) or pastes the stored password. Rejected: replacing the stored password (a stale paste could overwrite a newer shared secret) and keeping it without saying so (the operator believes the paste was saved). (2) `POST users/onboard` with a pasted `line` requires `settings.publish` (owner) as well as `customers.write`, because the line creates or changes home inventory through `home-exits/assign`, which `access-roles.ts` gates at `settings.publish`. An operator still onboards a customer without a pasted line, and binds an existing home with `homeExitId` (the same `customers.write` as `PUT users/{id}/home-binding`). Rejected: leaving the inventory write reachable by an operator through onboarding.
- Why stricter: both close a path that changed shared credentials or home inventory without the permission or the explicit step; neither widens exposure. The cost is one extra step for an operator who pastes a changed password, and an operator who pastes a home line at onboarding must ask the owner.
- Applied in: PR #1613 (`claude/foundations`), issue #1058.
