## 2026-10-02 · macOS：App 在已连接时死掉，出口随后不可达，helper 要不要自己放开网络

- Status: provisional. 「修这一条」是所有者的决定（2026-10-02，会话内，#1269）；按什么条件放开是 agent 按较严一侧选的。
- Chosen: helper 只在同时满足下面这些条件时放开：保存的状态是已提交会话（`tunnelInterfaces` 非空）；记录的属主（发起 arm/start 的 App 进程）确实已退出；没有进行中的原生更新；系统醒着，且有带路由器的 IPv4 主网络（主接口不是 utun/ipsec/ppp）；通过自己的 Core 做出口延迟探测（`/proxies/Tono-Exit/delay`），Core 自己连续答复「出口测试失败或超时」（HTTP 503/504），10 秒一次，两个互不相关的探测源（gstatic、cp.cloudflare.com）交替，第 7 次失败时放开（约 70 秒）。放开的动作和 bootstrap 孤儿一样：停 Core、`disarm`（AI 保持按 `automaticReleasePreservesAIHold`）、恢复 DNS、清属主。不选：#1269 的选项 1（属主死后固定 N 分钟就放开，不看出口）——隧道还通的时候也会把用户换成真实地址；选项 3（什么都不做）——出口坏掉后机器一直断网到重开 Tono；helper 自己换出口——目录和选择属于 App，helper 不持有。
- Why stricter: 出口还通就一直保持隧道和 PF，不因为 App 死了而放开。任何一项读不出来都按「不放开」处理：没有记录属主（helper 中途重启）、属主进程读不出、没有上行网络（那时任何出口都不通，网络回来后隧道自己恢复）、运行时配置读不出（不发探测，也就不计数）、探测还没返回、控制端口没答复或答复的不是出口结论（连接被拒、401、解析不了；连续失败从头算）、主网络是另一个 VPN。新的 arm/start 一律清掉之前的计数和探测；读不出新对端身份时属主记为未知，不沿用上一个。探测只发给 `127.0.0.1` 上自己的 Core 控制端口，密钥只从 root 的运行时配置读，不进参数和日志。放开之后机器是真实地址、没有 App 在提示，这是这条决定换来的代价：断网约 70 秒后恢复直连，而不是一直断到用户重开 Tono。纯 IPv6 网络没有 IPv4 主网络，这条不触发；Core 进程活着但控制端口不答复时也不触发；这两种情况行为和以前一样。两个探测源同时在出口侧不可达而出口本身还通时会误放开，这是剩余风险。
