## 2026-10-13 · What does a token rotated away on an active exit node get from the control plane?
- Status: provisional (the owner may overturn it; only the owner sets `owner` or `reversed`)
- Chosen: the superseded token is answered like a disabled node: `403 EXIT_NODE_DISABLED` (message "Exit node token was superseded by a rotation"), so the exit agent removes every client until the new token is deployed. Rotating an active node's token (`POST exit-nodes/{id}/token`) keeps the hash it replaces in `exit_nodes.revoked_token_hash`, the column disabling already uses; `authenticateExitNode` answers a hash found there with the 403 whatever the node's status. It authenticates nothing. Rejected: leaving the bare `401`, which the agent reads as "control plane unreachable", so it keeps serving its last roster and a revoked device keeps using that exit until the deployment (issue #1296).
- Why stricter: it closes a revocation gap at the cost of that node's availability for the length of the deployment delay (the normal procedure deploys the new token at once). Nothing new is authenticated. Only one superseded hash is kept per node, so a second rotation before the first old token was ever seen leaves that one at `401`; a disabled node's saved hash is untouched by a rotation. No migration: the column and its length check exist (migration 0081).
- Applied in: PR for issue #1296 (`claude/exit-token`).
