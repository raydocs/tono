## 2026-10-18 · A served exit that is not acknowledging: keep the whole catalog at 503, or serve the exits that have acknowledged?

- Status: provisional
- Chosen: serve only the exits that are active and whose `last_roster_at` is strictly after the credential being issued. A sibling that is disabled, missing, has never acknowledged, or whose last acknowledgement is older than 15 minutes is omitted from that response, including its ` · hy2` block, and does not hold the others at 503. A sibling that is active and acknowledged inside the last 15 minutes but not yet past this credential is omitted the same way while another exit is ready, and the catalog stays 503 `EXIT_IDENTITY_PROPAGATING` when no tracked exit is ready. An existing shared credential may still be served, only on the subset that has acknowledged it, and only while rollout is `dual` and that credential is not retired. It is never minted on this path. A catalog home with no `exit_nodes` row stays outside the gate. Routing `homeProxy` / `defaultProxy` that names an omitted proxy is left off that response; the binding row is not removed. Rejected: keep decision 055's all-served-exits gate (one dead published exit holds every newer device at 503); serve an unacknowledged UUID to the dead exit; mint a new device UUID to "retry" (that resets the acknowledgement clock).
- Why stricter: no UUID is written into a node that has not acknowledged it. Unhealthy nodes stop denying the exits that already hold the credential. A pending node is not treated as permanently dead, so a live exit that is one roster round behind still blocks when it is the only exit. Logout does not rotate the credential. Nothing here changes PF/WFP or protection release.
