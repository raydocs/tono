## 2026-10-02 · Windows：连接期间要不要放行局域网，放行哪些

- Status: provisional. 「放行局域网」是所有者的决定（2026-10-02，会话内）；具体放行哪些地址、端口和方向是 agent 按较严一侧选的。
- Chosen: 只在 `Locked` 且有隧道 LUID 时渲染，非持久。出站放行 `10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`fe80::/10`、`fc00::/7`，发现用的 `224.0.0.0/24`、`255.255.255.255`、`ff02::/16`，以及 SSDP 的 `239.255.255.250` UDP 1900；入站只放行来自上述单播段的对端。出站和入站的放行都不覆盖远端端口 53 和 853（SSDP 那条只有 UDP 1900）。核心进程（staged core）到这些地址另加一条阻断；核心的 app id 解析不出来、这条阻断装不上时，放行规则一并不装，已装的一并撤掉。不选：按网卡当前前缀放行（TunnelCrack LocalNet：恶意网络可以把公网段宣告成「本地」）；放行运营商 NAT `100.64/10`（macOS 也不放）；放行整个 `239/8`；做成用户开关（这一版不加设置项）；在放行之上再加一条 53 端口阻断（规则 E 的注释记录过：独立的 53 端口阻断在真机上打断过 Windows 的解析路径，所以改成放行规则本身不覆盖这两个端口，发往这两个端口的流量仍由改动前的规则决定）。
- Why stricter: `Bootstrap`、`Blocked`、没有 LUID 的 `Locked` 都不渲染这些规则。地址表是静态的私网段，不按网卡现算。局域网 DNS（53/853）不放行，系统解析器发给路由器的查询和以前一样被兜底阻断。核心进程到局域网被阻断，规则 H（WeChat 的 DIRECT）仍只到公网单播。入站只对局域网对端开放，Windows 防火墙在自己的 sublayer 里照常裁决。多放行的是：连接期间任何进程（核心除外）可以从物理网卡直连这些私网和链路本地地址（53/853 除外），局域网对端可以向本机发起连接。剩余风险，记录在此：这些地址段是「私网」，不等于「在网」。Windows 路由表把其中某个目的地指向物理网卡时（同网段；DHCP 或路由通告下发的更具体路由；任何 ULA，因为隧道不带 IPv6），包就从物理网卡出去并被放行，路由器再把它转到哪里，这条规则管不了。公网地址不在表里：这组规则不新增任何公网目的地址的放行，既有的出口节点和 DIRECT 例外不变。规则跟的是 Service 记录的会话（核心实例没变就保留隧道 LUID），不是网卡的实时存在：隧道网卡消失而核心实例没变的那段时间，公网和以前一样被阻断，局域网仍可达。地址表参照 macOS 的 `tono-lan`、`tono-linklocal`、`tono-ssdp`（[决策 045](045-2026-10-02-macos-lan-discovery-pf.md)），那边同样不限网卡；两边机制不同（PF 用独立的 DNS 丢弃规则和状态规则，IPv6 组播放得更宽），不是逐条等价。
- Applied in: [#1355](https://github.com/raydocs/tono/pull/1355)。
