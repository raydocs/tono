## 2026-10-13 · When SCM Stop's 60 s window ends while another task is still removing WFP, drop the runtime or wait?

- Status: provisional
- Chosen: wait, bounded. After the Stop window the Service waits up to 30 s for a WFP removal that is already inside the engine (one engine budget, `WFP_CALL_TIMEOUT` 25 s, plus slack), then up to 5 s for that release to write its tombstone, and only then drops the runtime. The wait never starts, skips or reverses a release; a removal still inside the engine at the end of the wait is left as it was and the next Service start releases a non-strict leftover (existing startup recovery). Rejected: shrinking the DNS (40 s) and WFP (25 s) release budgets to fit the Stop window, because a shortened DNS restore would refuse the release and keep the block; dropping the runtime at the Stop timeout as before, because that aborts the transaction.
- Why stricter: it removes a way for a non-strict machine to stay fully blocked after a Stop (decision 036: the user always has a network) without opening anything: the wait only lets a release that was already allowed finish. The cost, accepted here, is a Stop that can take up to 35 s longer than before in this race; SCM keeps getting its StopPending checkpoint during that time.
- Applied in: `settle_in_flight_wfp_removal` (`apps/windows/service/src/core/windows_kill_switch/engine.rs`), called by `stop_ipc_server`; issue #1284.
