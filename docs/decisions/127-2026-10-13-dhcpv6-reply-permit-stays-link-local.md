## 2026-10-13 · Should the armed WFP inbound DHCPv6 reply permit also admit relay replies whose source is not link-local?

- Status: provisional (the owner may overturn it; only the owner sets `owner` or `reversed`)
- Chosen: no. The inbound permit `intent/permit-dhcp-v6-in` (`apps/windows/service/src/core/wfp_model.rs`, UDP 547 to 546 on `ALE_AUTH_RECV_ACCEPT_V6`) stays bounded to `fe80::/10`. A network whose DHCPv6 relay answers from a global or unique-local source is a known limitation: while Tono protection is armed, that client gets no stateful DHCPv6 lease or renewal. Rejected: dropping the prefix check (any host on any network could then open a flow to the client's port 546 while the machine is otherwise blocked), and a prefix list of "relay-looking" ranges (no way to tell a relay from a rogue peer by address alone).
- Why stricter: AGENTS.md never loosens fail-closed WFP. The widened rule would be an unconditional inbound permit keyed on two ports only, which is the exact shape the existing test `a global peer cannot open a flow on the DHCPv6 client port` forbids. A safe widening needs an identity the packet cannot fake (the Dhcp service SID on `ALE_USER_ID`, or a server identity learned from the lease), and that is the same device-only unknown as TW-OpenAI-1 (#602), so it is one hardware task, not a code change now.
- Blast radius, checked in code: only the `intent/permit-dhcp-v6-in` filter is involved. DHCPv4 inbound (`intent/permit-dhcp-v4-in`) is port-only with no address bound, so IPv4 relays and servers on any address still answer; the outbound DHCPv6 client permit (`intent/permit-dhcp-v6`) reaches `ff02::1:2` and `fe80::/10`, so the request still leaves. IPv6 addresses from router advertisements (SLAAC) rely on the NDP permits, which are untouched. The tunnel's own permits are separate filters, and the tunnel carries no IPv6 (see the comment on `lan_rules` in the same file). A machine that needs stateful DHCPv6 from a global-source relay therefore loses only its IPv6 lease while protected; its IPv4 lease and the tunnel are unaffected. Native Windows behavior on such a network is unrun (no device).
- Applied in: no code change. Finding WIN-DHCPV6-RELAY-SOURCE (#1056). Related: decision 097, finding TW-OpenAI-1 (#602).
