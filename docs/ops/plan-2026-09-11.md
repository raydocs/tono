# Tono 运维后台 · 剩余工作完整计划（详细版，2026-09-10 晚定稿，交给执行 agent）

## Context

Tono 是自营 VPN 产品：macOS / Windows 客户端 + Cloudflare Worker 控制面（`services/control-plane`，D1 数据库 `tono-control-plane`）+ 一台 hub 收集器（`ops-panel/collect.py`）+ 十几台出口节点。2026-09-08 的大陆连接事故暴露出旧后台答不出「哪个客户在哪个节点、哪一步失败」。09-09 起按 `docs/ops/` 方案重建了运维后台 `services/ops-console`（React 19 + Vite + Tailwind v4 + shadcn，部署在 `admin.afk.ccwu.cc/ops2/`，Cloudflare Access 之后）和 Worker 侧的 `services/control-plane/src/ops/*`。两天 12 次生产部署，迁移到 0067（`ops/platform` 上已到 0071），Worker 840+ 测试，控制台 296 单测 + 331 条 Playwright 基线。

产品打分 7.2 / 10。差的一截：告警链路证明能开事故、能排队投递，但没放 Telegram 令牌所以叫不醒人；客户端两端的「失败即报 / 日志上传」分支推了没合；节点没有不可变身份和故障域；客户列表先读全员再截页；部门 D 三条实现线是 WIP。本计划把剩下的全部写成可独立执行的任务：每条有目标、背景、文件与函数、数据与接口形状、步骤、唯一的测试、验收命令。执行 agent 不需要本会话的任何上下文。

结论先写清：**保留 VLESS/REALITY TCP 为主通道，新增 Hysteria2（UDP/QUIC，自带 TLS 1.3）为备用通道，客户端在 TCP 握手失败后自动切换。** UDP 也可能被运营商限速或阻断（RFC 9308 §2），所以两条都留；它不替代本地保护 / WFP / TUN / DNS 的修复，也不解释 Mesa 的真实故障——那条继续查。两端核心都是同一份 pinned mihomo，mihomo 原生支持 `type: hysteria2`，所以客户端侧的核心不用改，改的是目录、连接编排、Windows 的 WFP 端点和遥测。

**7.0 先证明 UDP 在目标运营商能通**（老板 + Fable · S，不通就停）
- 一台节点（选东京一台）手工装 `hysteria2` server（官方二进制，`listen :443/udp`，自签证书，记指纹；带宽 `up/down` 先不设限），客户端用 mihomo 手工配置 `type: hysteria2` + `sni` + `skip-cert-verify: false` + `fingerprint: <sha256>` 连一次；用三网真机（电信 / 联通 / 移动各一台或朋友帮测）各测 5 次握手与 30 秒下载。任一运营商 UDP 完全不通就只做「手动可选」，不做自动切换。结果写 `docs/ops/transport-hy2.md`。

**7.1 节点侧**（Grok · M，`ops-panel/` + provisioner）
- provisioner 加 `hysteria2` 角色：装二进制、systemd、自签证书（`openssl` 10 年，指纹写回 `ops_node_profiles`——迁移 0076 `hy2_port INTEGER, hy2_fingerprint TEXT, hy2_obfs_ref TEXT`，可空）、`ufw` 放行 UDP 端口、和 Xray 共存（不同端口或 UDP 与 TCP 同端口 443）。密码 = 该节点 exit token 的派生（与 VLESS 的 `{{TONO_CLIENT_UUID}}` 占位一致，Worker 在 `catalog-yaml.ts` 的 `filterCatalogYamlForUser` 里替换）。
