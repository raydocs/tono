# Tono 工程质量整改与自动化验收任务书

日期：2026-09-21。性质：所有者授权的工程整改执行契约，不是完成报告或发布许可。

面向 Amp Orb 的独立主线程；无需本地聊天上下文。请完整阅读本文后开始执行。
本轮允许必要的底层大改，要求连续完成调查、实现、验证和 GitHub 交付，不能只交建议清单。
本文服务于客户 [SHIP_PLAN](SHIP_PLAN.md) G1–G3 的工程证据和
[运维计划](ops/plan-2026-09-11.md) 的对应任务；不替代两份计划，不新增或关闭客户发布门。

## 1. 目标：全面找错，完成整改，留下可追溯证据

连接和恢复问题已持续约一个月。所有者愿意投入 Astra Max 与 Orb 成本，要求全面、深入地
检查约定范围，而不是找到少数容易修复的问题、提交 PR 后就结束。

交付目标：

1. 关键模块职责清楚，状态、后台任务、系统资源和清理操作有明确所有者。
2. 连接、切换、取消、超时、重连及恢复的契约一致，可重复测试。
3. 已确认的重要范围内缺陷完成修复；必要时从结构上消除反复出现的同类缺陷。
4. 出错时能关联实际运行身份、失败阶段、责任层、原因链和恢复结果。
5. 代码、测试、工程约束和验收记录一起交付；证据对应最终组合源码。
6. 清楚区分工程验收、实机验收和客户发布资格。

不承诺或宣称“找出了所有 bug”。完整性指覆盖清单有交代、确认问题有闭环、未知没有被隐藏，
不是模型打分、文件数量、测试数量、覆盖率数字或重构规模。
不要迎合“代码一定很差”的预设；正常且有证据的实现应保留。

## 2. 模型、职责和并行规则

- 主负责人和承担分析、实现、独立审查的子线程均明确使用
  **GPT-6 Astra Max**，模式键 **`gpt-6-astra-max`**。
- 开始时核对实际可用模式。普通 Ultra 不是该模型的替代名称。若普通 subagent 无法明确
  指定或确认模型，使用可指定模式的独立子 Orb；无法使用指定模式时报告阻塞，不悄悄降级。
- 主线程亲自理解端到端调用链、关键不变量和锁顺序，负责架构选择、优先级、集成及最终结论。
  不得仅汇总子代理报告。
- 默认最多同时运行两个子 Orb。核心连接与恢复链路默认一个实现者，不按文件任意拆分所有权。
  子线程不得递归创建更多实现线程。
- 仅并行处理真正独立的模块或证据任务。同一文件一个写入者；修改共享接口前协调。
- 每个子任务说明目标、准确源码 SHA、文件范围、契约、验证方法、完成条件和应返回的证据。
  新 Orb 不继承本地提交、未提交文件、服务或环境；先确认源码和依赖可达，必要时显式传输。
- 主线程检查实际 diff、测试日志及来源，解决接口冲突。各分支分别通过不等于最终组合通过。

## 4. 全范围清单与用户故障地图

先枚举全部第一方模块、交付程序、关键接口、持久化状态、后台任务、安装更新路径和 CI。
逐项标记已审查、已验证、存在问题、受阻或未覆盖；暂不检查必须给理由。
第三方代码不要求逐行审计，但其版本、补丁、信任边界和关键依赖契约需要检查。

至少覆盖下列领域，并为每项映射到 G1/G2/G3 或既有 ops 任务：

| 领域 | 必须理解的路径 |
|---|---|
| Windows App | UI 命令、状态投影、任务注册、连接编排、控制器、节点选择、DIRECT、重连 |
| Windows Service / 共享核心 | IPC 权限与身份、Core 生命周期、WFP、TUN、路由、DNS/NRPT、持久化恢复 |
| macOS | UI/协调器、helper、Core、PF、DNS、对应的取消与恢复契约 |
| 控制面 | 登录与授权、凭据、设备、签名目录与策略、版本兼容、失败证据接收 |
| exit-agent / home-agent / collector | 凭据同步、就绪证据、配置应用、重试与报告、相关身份和计量契约 |
| 运维 UI 与工具 | 错误证据是否真实可用、共享协议、脚本边界；不另起无关视觉改版 |
| 安装与更新 | App/Service/Core 交接、更新日志、升级失败、卸载恢复、实际运行版本 |
| 工程基础 | 依赖锁定、构建、CI 路径覆盖、测试隔离、产物来源、其他客户端及未交付组件 |

Windows 连接与恢复链路优先深入；不能因此把未检查平台写成“全仓通过”。
运维问题单独归属运维计划，不将其任意变成客户发布门。

从用户症状建立：**症状 → 候选失败阶段 → 区分原因需要的证据 → 可重复验证**。
至少处理无法连接、连接很慢、界面卡顿、显示已连接但无流量、切换后断网、断开后无法恢复网络。
例如“已连接但打不开网页”需区分旧 UI、出口不可达、DNS 故障、路由/WFP 不匹配和迟到任务破坏。
这些是待证实的分支，不能预先选一个当根因。

## 5. 运行身份与证据边界

检查诊断能否证明客户实际运行的 App、Service/helper、Core 身份，而不仅是磁盘上存在的文件：

- 版本、构建来源及可获得的二进制身份；Service 实际路径、进程/会话身份和协议版本。
- 目录 revision、策略版本/摘要、实际应用配置的身份，以及缓存和已应用状态的区别。
- 升级后旧进程、旧 Service 注册路径、旧 Core 或旧配置仍被使用的检测与报告。
- 依据真实兼容矩阵判断是否兼容，不能要求各组件版本号简单相等。

没有客户诊断或设备访问时，只能验证采集与判断机制，列出缺失证据，不能声称客户安装已确认正确。
不得用新源码解释旧安装包的全部行为，不得假定安装完成就等于后台组件已替换。
Windows Education 不证明校园网；TLS EOF 不证明审查、UUID 错误或服务端主动拒绝。
比较其他客户端时必须注明节点、协议、凭据、网络及系统代理/TUN 模式是否可比。

## 6. 质量标准和允许的大改

### 6.1 关键工程契约

对关键状态回答：谁写入、谁验证、谁取消、谁清理；调用者消失后责任由谁承担？
UI 展示的是意图、缓存还是经过读回验证的事实？OS 事实与 UI 事实冲突时谁有最终权威？

重点检查：

- 单一状态来源、合法状态转换、任务和资源归属、跨进程协议与权限边界。
- 锁顺序、持锁 I/O、递归等待、检查到副作用之间的竞态窗口。
- 超时是否只停止等待；取消后 IPC 是否仍可能提交；旧结果是否污染新会话。
- 重试的总预算、幂等性、队列上限及终止条件；后台任务是否被监督。
- 部分成功和恢复失败能否被明确表达；是否错误地依赖后续监控补救遗留事务。
- 吞错、失败返回成功、脆弱字符串判定、缺少读回却宣称回滚成功。
- IPC/文件/网络输入的大小和类型边界、原子存储、崩溃一致性、权限及凭据隔离。
- 主线程阻塞、重复轮询、配置重复生成和不必要的串行等待。

### 6.2 授权必要的底层重构

若局部补丁不能可靠保证契约，允许重构状态机、代际、取消与清理编排、模块边界、IPC 契约、
系统策略应用/恢复协调、诊断和测试结构。不要因为改动较大就退回零散补丁。

每项结构性修改先说明具体失效机制、局部修复为何不足、保留的产品行为、新边界和验证方法。
不要只靠增加检查分支处理所有权问题；也不要为模仿参考项目更换技术栈。

代码整齐意味着职责与控制流清楚、规则来源明确、名称准确、错误路径可追踪。
不以文件长短判断质量，不制造纯转发包装层，不做无关全仓格式化、重命名或依赖升级。
遵守 AGENTS.md 中 Windows workspace、macOS 目录和特权路径兼容名称的限制。
若确需突破既有硬约束，先给出具体理由和替代契约，申请决定，不能默默忽略。

每发现一类根因，检查该类问题在相关生产调用点是否重复出现；保留证据，不无限扩展到无关重写。
纯重构与行为修改分开提交，保留可回退边界，避免旧新实现长期同时拥有状态写入权。

## 8. 故障必须能定位，但原因未知时保持未知

复用现有诊断体系，先找真实缺口，不新增平行日志平台。
关键操作按实际可获得证据关联：

- 操作/尝试关联标识、连接代际、跨层请求身份；标识不得成为新的鉴权凭据。
- App/Service/helper/Core 构建身份、目录与策略/配置身份。
- 阶段、耗时、最后成功步骤、失败层与稳定错误码。
- 脱敏原因链、可获得的 OS 错误、主动取消/超时/过期结果的区别。
- 已发生的副作用、恢复成功/失败/未知、是否仍受保护、重试依据及用户可采取的动作。

区分“发生在哪里”和“为什么发生”；不能仅凭底层错误字符串断言网络封锁。
用户提示简明，工程证据保留原因链但不暴露凭据、私钥、令牌、完整配置或不必要个人数据。
日志具有容量、保留时间和队列边界；写日志失败不能阻塞连接或使保护失效。
若需要远端上传或新增遥测，先遵守现有同意、账户隔离、保留和上传契约；不擅自扩大数据披露。

至少对代表性失败证明：跨层记录属于同一操作，没有拼入新会话，原始原因仍可识别，恢复结果真实，
脱敏有效。对无法复现的高影响症状，明确缺什么证据，补最小记录能力，让下次失败能区分候选原因。

## 9. 自动化验证：生产路径、受控故障和反例

### 9.1 验证分层

1. 静态/工程：相关类型、编译、现有 lint/格式、依赖锁定、协议/版本与构建契约。
2. 行为：真实状态机、输入边界、错误分类、持久化和恢复决策。
3. 组合：状态机、任务注册、IPC 编排、配置应用和清理之间的实际生产调用关系。
4. 原生/系统：在仓库允许的隔离托管环境执行可行检查，明确其与客户 OS 的差异。
5. 后续实机：安装、实际网络接管、休眠、崩溃恢复、国内线路等缺口单列，不冒充已通过。

先盘点现有测试和命令，不默认建设新框架。局部修改先跑定点检查；共享状态机或跨模块重构
执行相应更广验证；最终在组合 SHA 上运行必要验收。不要每个小改动都重复全量构建。

### 9.2 可重演的失败时序

在现有依赖边界控制以下情况，优先覆盖确认风险：

- 暂停 A 的 IPC，完成 B，再释放 A 的迟到结果。
- 操作成功到一半，下一步失败或读回失败。
- 连接中断开、快速节点切换、并发释放、DIRECT 与切换竞争。
- 超时与主动取消同时发生；调用者退出但后台副作用继续。
- Core/Service 重启、旧会话返回、配置/凭据版本错配。
- 慢磁盘、慢服务查询、损坏/过期日志、权限拒绝、持久化失败。
- 重复回调、同一请求重试和副作用幂等性。

使用 barrier、channel、受控时钟和明确断言，不依靠长 sleep 或无界随机重试碰运气。
外部 OS/网络可在清楚的边界注入故障，但不能 mock 掉整个连接流程。
测试必须观察最终状态、实际提交/清理的归属和保护结果，不能只断言 mock 调用次数。

每个已确认缺陷先写聚焦回归，观察旧实现以预期原因失败，再修复并确认通过。
构建错误和 fixture 初始化失败不算行为复现。遵守每个行为一个聚焦回归的仓库规则。
对关键测试用有代表性的错误实现或受控变异验证其检错能力；不要硬编码迎合测试。
适合的状态机、解析器可使用模型/属性测试或有界 fuzz，记录预算、种子和最小失败输入。
是否使用取决于风险和收益，不以工具数量体现质量。

### 9.3 执行环境与权限

- Orb：源码工作、适合 Linux 的前端/控制面/便携逻辑检查、证据整理。
- Windows/macOS 原生检查：遵循 BUILD_AND_TEST.md，使用已有 GitHub 托管 CI。
  不把 Linux 模拟、托管 Windows Server 或构建成功写成客户 Windows 11 实机合格。
- 不在编辑用 MacBook 自动运行原生构建，不注册永久自托管 runner，不复活已退役构建环境。
- 允许提交代码及触发必要的普通、非部署 CI；发起前检查 workflow 的实际副作用。
  不重复触发已在运行的同一检查，采用有界等待，pending 可以如实交付。
- 特权安装、网络故障注入和破坏性系统检查仅使用已有、获准的可恢复隔离环境及其防护门。
  不对客户设备、生产节点、共享数据库或日常机器试验。
- 缺少环境时报告未执行及最小外部需求，不默默回退到不允许的执行地点。

## 10. 四阶段连续执行，不停在报告或首次 PR

| 阶段 | 必须形成的成果 | 进入下一阶段前核对 |
|---|---|---|
| 基线 | 源码/产物身份、覆盖清单、故障地图、当前检查结果 | 目标源码正确，基线失败已分类 |
| 定位 | 确认问题、同类调用点、复现与诊断缺口、必要架构决定 | 区分事实/推测；有可检验的契约 |
| 修复 | 代码、测试、必要结构性整改、分阶段提交与 PR | 不削弱保护，不混入无关改动 |
| 组合验收 | 最终组合 SHA、执行证据、独立反证审查、剩余缺口 | 分支证据不能冒充组合证据 |

审查后维护有限的本轮整改清单，区分正确性/保护缺陷、工程缺陷、可延期技术债和风格偏好。
范围内的重要确认问题不能因为“不容易修”被静默延期。允许纳入直接依赖和修复引入的回归，
但不要每修一项就重新启动无边界全库审计。阶段切换不要求用户逐步确认。

重大改动应由独立 Astra Max 线程针对具体契约做反证审查，尝试寻找失败顺序和漏测边界；
主线程核实结论，不以“reviewer 通过”替代执行证据。

若涉及无法本地决定的产品行为、安全/权限策略改变、持久化迁移或真实外部权限，先完成不依赖
决定的部分，再集中提出具体问题。允许编写迁移并对临时数据验证，不授权在共享数据上执行。
同一阻塞连续两次未解决，停止重复原路径，保留成果，给出证据及最小下一步；不递归召唤代理。

## 11. GitHub 交付和验收矩阵

形成可保留成果即 commit、push 独立分支并创建/更新 PR，不等所有工作结束才上传。
拆分提交或依赖明确的 PR 是审查与回退手段，不代表拆成多轮等用户催促。
每项 PR 指明 G1/G2/G3 或对应 ops 任务；遵守发布线，不把不相关交付混到同一集成分支。
提供最终组合分支及各 PR 的集成关系。未合并分支之间的文件/提交必须真实传递，不只发 SHA。

提交前检查暂存 diff、密钥、个人数据、缓存和无关产物；不覆盖他人工作、不重写已发布历史。
验证未完成或仍有实质阻塞时保留 Draft。不能将“上传成功”表述为“验收通过”。
无法 push/建 PR 时保留 commit，给出具体阻塞和恢复交付命令。

优先复用合适验收文档；必要时新增一份本轮记录，避免多份重复报告。
每条证据至少包含：

| 字段 | 内容 |
|---|---|
| 模块/行为与契约 | 验证什么，错误实现会怎样 |
| 证据类型 | 源码确认、自动化复现、检查、集成或实机 |
| 方法与环境 | 实际命令、命名测试、OS/依赖/故障条件 |
| 源码身份 | 完整 SHA、CI checkout 来源、相关产物身份 |
| 结果 | 通过、失败、未执行、环境阻塞或沿用 |
| 来源 | 日志、CI run/job、代码位置；公开内容须脱敏 |
| 限制与归属 | 不能证明什么，剩余问题/Issue 和责任范围 |

保留基线失败和修复前后证据。不删除断言、降低阈值、扩大 skip/allow 或改测试目标制造绿灯。
配置了检查不代表执行过；跳过、排队、日志缺失、旧 SHA、辅助函数通过都不等于完整验收。
`acceptance_check` 可运行一次现有定点命令并记录证据；`acceptance_status` 可检查已有回执是否过期。
没有这些工具时记录同样可追溯的命令结果。SuperCov/Jev 可选，不为评分增加无关工作；
任何分数和命令 exit 0 都不能单独证明全部需求满足。外发源码遵守工具的明确同意要求。

## 12. 不可突破的边界与最终完成标准

保持 fail-closed，不允许跳过 TLS 证书验证、绕过特权服务、静默直连或伪造 Connected。
不通过取消真实流量验证改善表面连接率；探测网址/策略变化须有实际契约依据，不反复推翻已定产品选择。
不自动 merge、push main/master、force push、部署、签名发布、创建发布标签、发布软件包或推进
Sparkle/appcast、`windows-updates`、客户更新 JSON。生产节点、共享数据库和客户渠道操作另需授权。
不把本文当作调度授权：无后台无限运行、无自动续开轮次、无未创建 schedule 的跟进承诺。

本轮完成要求：

1. 约定覆盖清单全部有交代，没有将未检查模块写成通过。
2. 重要的已确认范围内问题已修复；若仍有阻塞，明确结论为“未完成/受阻”，不能报全绿。
3. 关键变更有能检出错误实现的证据，组合验证对应最终提交。
4. 代表性故障能被关联和定位，敏感信息保护与日志边界经检查。
5. 代码、测试和验收记录已交付 GitHub，PR 关系和剩余外部需求清楚。

最终报告必须自包含：仓库/分支/提交/PR、覆盖范围、确认并修复的问题及证据、结构性改进理由、
诊断现在能回答什么、最终检查的通过/失败/未执行项、实机与客户网络缺口、剩余风险和最小下一步。
不要只给总分、长篇建议或子代理结论。

最后分别回答：**代码与工程层面是否达到本轮验收要求？是否具备进入后续实机验收的条件？**
即使两项都通过，也不代表客户发布门已通过，更不能宣称已经消除所有 bug。
