## Findings（按严重度排序）

### F1 — Major / P1：系统重新发布旧通知时，无 VPN 仍出现 Connected

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/engine/TonoNotifications.kt:60-70`；`surface/EngineWatch.kt:162-181`；`surface/NotificationWatchdog.kt:98-124`。测试容忍窗口：`src/androidTest/kotlin/com/raydocs/tono/mobile/LocalTunnelDeviceTest.kt:885-895`。
- **实际场景/证据**：真实 MainActivity/libbox 连接本地替身，关闭 Activity，杀死引擎。原始 `ci-redacted-text/retry/local-tunnel-t6.txt` 的 Doze 样本在 **1236ms** 为 `vpn=false title=Connected phase=CONNECTED surface=UNKNOWN`，到 **1354ms** 才为 Connecting；同时杀 watch 的样本在 **1173ms** 同样错误，1277ms 才转正。首轮也分别在 1282ms、1164ms 观察到这个组合。是 Android 重贴上一条 ongoing notification，watch/new engine 随后纠正，不能将测试通过解释为从未误导。
- **影响**：系统表面与当前公共状态相互矛盾，隧道已经不在却仍给肯定连接声明，违反本次明确的安全不变量。日志中的 104–152ms 是观测点间隔，不是经过逐帧证明的持续时间上界；未看到此精确窗口的截图，不虚构其像素外观。最终 stopped 原图只能证明最终收敛。
- **建议**：可被系统持久化重贴的 foreground 通知使用非当前保护断言（运行中/有时间限定的“上次确认”），或采用能阻止旧肯定声明重新出现的通知协议；实时 Connected 不能仅靠死亡后轮询补救。给系统重贴路径增加断言，明确区分“最终纠正”与“从不在无 VPN 时声称已连接”。
- **确认级别**：原始运行日志直接观察；未在本机重跑。**触发严重状态误导否决。**

### F2 — Major / P1：Android 系统保护标志只在启动隧道时读取，保护解除后仍可声称不会直连

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/engine/TonoVpnService.kt:414-418`；`ui/SettingsScreen.kt:117-130`；`res/values/strings.xml:112`（中文对应 `values-zh-rCN/strings.xml:111`）。
- **具体场景**：以 Always-on + lockdown 开启状态连接，随后从设置页的 Open VPN settings 关闭“屏蔽未使用 VPN 的连接”，保持当前 VPN 运行，再返回 Tono。引擎只在 `startCore` 成功后采样这两个字段；`EngineClient.resume()` 只是取旧 snapshot，流量心跳、普通状态写入及断开都不会重读。设置仍可显示“Tono 停止时应用会等待，不会直连”，尽管系统保护已经撤销。
- **影响**：这是对故障/重启后保护的错误肯定声明，不是装饰性状态延迟；设置页也没有 EngineLink 新鲜度门禁。全局搜索确认生产代码中仅该启动处写入系统标志。
- **建议**：从 Android 设置返回时通过引擎重新查询系统保护；将这类声明与独立的新鲜度绑定，读取前/引擎失联时显示未知或保守提示。加一条“开启连接 → 外部关闭 lockdown → 返回页面”的回归，不用 fixture 的固定布尔值替代。
- **确认级别**：源码可达路径；没有相应运行测试/截图，不声称已设备复现。**按严重保护声明错误处理。**

### F3 — Major / P1：异步认证/目录 IO 在旧账号或操作取消后仍可提交身份与持久化数据

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/engine/TonoVpnService.kt:249-264,284-292,309-316,327-345,678`；`engine/EngineStore.kt:87-97`。
- **具体场景 A**：验证码验证请求尚未返回，用户点 Use another email（`ui/SignInScreen.kt:117-119`），`cancelLogin` 只清空 LoginView；旧 verify 成功后不检查请求/账号 epoch，仍保存旧账号令牌并进入 IDLE，违背用户已经切换的登录意图。
- **具体场景 B**：A 的 refresh/catalog 请求在 IO 线程挂起，用户退出 A 并登录 B。A 的 IO 返回后，`bearer` 和 `loadCatalog` 会先直接写令牌、目录及目录元数据；`ledger.isCurrent(gen)` 只在这些写入之后检查。即使旧 snapshot 被拒绝，旧账号目录仍能覆盖新账号缓存，离线回退可能让 B 使用 A 的出口/Home 身份。
- **影响**：隧道 attempt fence 并不等于账号 fence，旧异步结果可以恢复取消的身份或造成跨账号缓存混用；Keystore 加密不能解决这个逻辑归属错误。
- **建议**：IO 只返回数据；所有令牌/目录/快照提交在 engine executor 上，提交前检查账号 epoch + 登录请求 ID。退出、换邮箱、成功切换账号时使旧请求失效；串行化同账号 refresh。增加延迟响应跨 cancel/sign-out/account-switch 的单条行为回归。
- **确认级别**：源码交错推导，未执行新的 fault injection；现有 75 个状态矩阵测试不涵盖这些账号提交路径。不宣称已经观察到实际账号泄露。

### F4 — Moderate / P2：同一隧道内的旧探测可以覆盖新网络/新一轮重检结果

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/engine/TonoVpnService.kt:430-440,490-506,701-703`；`engine/TunnelAuthority.kt:80-93`。
- **具体场景**：已连接后发起一次较慢重检，切换到另一网络并再次重检；两次都使用同一 `ledger.attempt`。较新的失败结果先提交，旧网络的成功结果后到，仍会被 `probed` 接受，页面回到 Connected 并显示旧出口国家。完全丢失底层网络时，IPv4 → 无网络还可能不触发任何重检，保留旧的 OK。
- **建议**：给每次探测和底层网络各自绑定代数/身份；只接受最新探测、同一底层网络的结果。网络丢失立即撤销出口可用性声明；保持 fail-closed 路由，但不要把历史出口结果当当前结果。
- **确认级别**：源码交错推导；没有真实网络切换 fault evidence。现有旧 attempt 测试不能覆盖“相同 attempt，不同重检”。

### F5 — Moderate / P2：实际捕获中关键标题/主按钮文字会消失，语义树通过不能证明可见

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/ui/HomeScreen.kt:193-219,344-356`；持续绘制/降级相关 `ui/SeaScene.kt:66-79`。
- **原始像素/运动**：首轮 `ci-tunnel-visuals/evidence-attempt-1792442809/local-t3-connecting-missing.png` 有 Connected、00:10 和线路胶囊，但 **Disconnect 与 Local test 的可见字形为空**；同刻 XML 却包含这些文字。不是凭文件名推断。重试原录屏第 274 帧（PTS **107.811644s**，本报告 `derived/local-f05.png`）在断开附近同样缺失状态标题、说明和按钮文字，只剩旧计时/白天装饰；下一原始帧已转夜色和 Not connected。正常 JVM/设备连接切换帧也有很低透明度的关键字。
- **限制**：这是软件 GPU 模拟器上的真实绘制/采集现象，不据此断言实体手机也卡顿或字形永久丢失；截图缺字的具体根因没有被证明。不能把仅遍历 TextLayoutResult/semantics 的可访问性检查当可见像素检查。
- **建议**：安全相关标题和主操作标签即时替换或保证至少一份始终可读，不使用同时低透明度的双动画；动作语义与可见字同步。对持续重绘增加低性能自动降级，补实际帧级可见性与真机证据，而不是只延长等待或提高健康阈值。
- **确认级别**：已逐张打开原图，并解码原始视频连续帧；不以本项单独认定真机一票否决。

### F6 — Moderate / P2：首页线路胶囊仍显示 desired 而不是 confirmed 身份

- **位置**：`apps/android/mobile/src/main/kotlin/com/raydocs/tono/mobile/ui/HomeScreen.kt:374-395`；`engine/TonoVpnService.kt:680-685`。
- **具体场景**：Tokyo 已确认连接时选择 Los Angeles。引擎先发布 `selectedNode=LA` 的旧 Connected 快照，再另发 reload 快照；首页始终用 selectedNode 取名称/延迟，不使用 appliedNode，且没有“所选/待应用”限定。第一条 snapshot 仍有 Tokyo 的 applied 确认，但用户可以看到 Connected + LA；延迟若已有缓存仍可亮绿。公共表面与 Lines 的 In use 反而正确使用 applied 身份。
- **建议**：已连接时首页主线路显示 appliedNode；desired 不同时以明确待应用状态呈现，或把选择与撤销确认合成一次状态提交。延迟标记其测量性质/新鲜度，不能替代当前线路确认。
- **确认级别**：源码直接存在的中间状态；未提供双节点实际切换录屏，未声称这个中间状态每次都会被 Compose 绘成一帧。
