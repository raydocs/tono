## Open decision item: lifetime peer baseline retention

`HOME-AGENT-PEER-RETENTION-CAP` is distinct from issue #5 counter-generation handling. `attribute_peer_counters` retains every stable peer baseline indefinitely, while `validate_state` uses the current-inventory limit (2,000) on that lifetime history. Ordinary identity churn can leave 2,000 retired baselines with only one current peer. Adding peer 2,001 makes `save_state` throw before fresh POST and metering ACK. The durable state remains at 2,000, so every later observation repeats the failure. The reporter is explicitly undeployed, hence P2 rather than a live outage claim.

A fixture using the actual loader, attribution and saver persisted 2,000 valid baselines, attributed one new stable identity, then reproduced `invalid state schema` with 2,001 in memory and 2,000 still on disk. Blindly deleting absent peers risks charging old raw history again when a stable ID returns. Safe retention requires explicit counter-continuity/retirement semantics; no speculative pruning or accounting change is included.
