# Tono 手机端 UI 返工复盘（iOS #1672 / Android #1673）

2026-10-19 · 只读复盘，没有改代码，也没有触发 CI。数据来自 GitHub Actions 的全部运行记录、`docs/agent-reports/` 里的盲审原文，以及 Puck 转来的两个 orb 的自述。

## 现状
- 约 38 小时里，iOS 提交了 70 个 commit，Android 53 个。CI 运行 105 次，只有 29 次是绿的：iOS 53 次绿 14，Android 52 次绿 15。CI 一共耗时约 61 小时，其中 iOS 是 macOS 机器上的 27 小时，Android 是 Linux 上的 34 小时。
- 独立盲审的分数一直在原地打转：
  - iOS：83/83 → 83/87.5 → 84/86 → 81/86 → 83.5/84
  - Android：79.5/83 → 81.5/86 → 82/81 → 81/80
  - 实施方的自评始终比盲审高 2–8 分（91.5、89.5、87.5、86；Android 88、88、87），之前报给你的 91、88 都是自评。
- 评分表本身的及格线是 85 分、每项不低于 70%，且不触发一票否决。到现在两端都还没有过这条线，离 95 更远。

## 根因（按影响排序）
1. **状态真实性在架构上有缺口，每次都是逐个打补丁。** 最近 7 轮盲审里（iOS r8–r11、Android r6–r8），GPT 有 6 轮投了一票否决，iOS 第 10 轮 Opus 也投了否决，理由全是"严重状态误导"。iOS 依次被否在：模式切换被拒后界面显示新模式（r9）→ 回滚失败后心跳照写（r10）→ 没确认的线路显示成"当前"（r11）。Android 依次是：应用关闭后引擎挂了，通知栏还显示 Connected（r7）→ 这个窗口长达 57 秒（r8）→ 加了 watch 修这个，结果把重连后真实的 Connected 也误删了（Puck 的更正）。每补一处，下一条状态路径就会被找出来。没有一个统一的"只有隧道确认了才算数"的状态机和故障矩阵，否决就会一直有。
2. **Android 的 CI 大多是基础设施问题，不是代码问题。** 32 次失败里，29 次日志出现 adb `device offline`，只有 2 次出现标准的测试断言失败，另外 3 次是早期构建失败。每个分片都冷启动 x86_64 API 34 模拟器，没有 AVD 快照缓存。"换个新模拟器重试"跑了 42 次，用掉 633 分钟，占 Android CI 总时长的 31%。tunnel 分片中位数 24 分钟，最长 74 分钟，有一次 55 分钟超时。所以很多"绿"其实是靠重试才过的。
3. **iOS 的 CI 很慢，而且每次推送都跑完整套件。** iOS CI 中位数 34 分钟，最长 69 分钟。主要耗在设计预览截图（中位 17.8 分钟）和 UI 加无障碍审计（中位 14.8 分钟）。Libbox 每次都重新编，约 4.6 分钟，因为缓存只缓存了下载的东西。20 次 UI 失败里约 18 次是对比度或无障碍审计没过，而且很多轮是在修测量工具本身：CI 判 4.8:1 通过的按钮，盲审拿原图一算低于 4.5:1。
4. **推送比 CI 跑得还快，评审对象一直在变。** 推送间隔中位数 iOS 48 分钟、Android 33 分钟，约 38% 的推送离上一次不到 30 分钟，赶在上一轮 CI 跑完之前。结果 18 次运行因为 `cancel-in-progress` 被取消（iOS 13 次，Android 5 次）。一边改、一边评、一边重跑，每一轮都要拖好几个小时。
5. **有些分数没有真机根本拿不到。** "真实性/性能"这项 5 分，两端盲审都只给 3–3.5 分。Android 的性能数据是在软件 GPU 上测的：98.6% 的帧卡顿，帧时中位 350 ms，盲审明确说这"不是性能结论"。玻璃材质、状态动效、无障碍（VoiceOver/TalkBack 没有真人听过）也因为"真机没验证"一直被扣分。iOS 的真实小组件在没签名的构建里只会显示"Status unavailable"。按最新一轮两份盲审的平均扣分，丢分最多的项是：iOS 无障碍 −3.25、单手 −2.75、玻璃和动效各 −2.5；Android 动效 −5、玻璃 −4、单手 −3。
6. **自评偏高，误导了节奏。** 自评每轮都比盲审高几分，而且漏掉了每一个否决点。照自评推进，总以为"再改一轮就好了"。

## 新流程建议
1. **先把状态模型一次性修对，暂停打磨视觉。** 两端各定义一个单一的状态来源：只有隧道确认过的状态才能显示成"已连接"或"当前线路"，确认不了的一律保守显示。App、小组件、通知、磁贴、实时活动都读这一个来源。再写一份故障矩阵覆盖各种异常：引擎挂掉、重载被拒、回滚失败、App 被杀、Doze、并发写入。这些都做成单元测试或 JVM 测试，跑完只要几分钟。
2. **CI 分两条线。**
   - 每次推送跑快线，控制在 10 分钟以内：单元、JVM、TonoKit 测试，lint，构建，状态故障矩阵，再加少量截图对比。
   - 慢线每晚跑一次，冻结评审前再跑一次：完整的 UI、无障碍、设计预览截图，以及 tunnel 分片。
   - iOS 按源码 hash 缓存 Libbox.xcframework。Android 加上 AVD 快照缓存，首跑和重试的次数都记下来，不稳的测试先隔离，不靠重试刷绿。
3. **对比度的测量方法先校准一次，然后锁定**：用已知的样本校准，算法定为"字形对比它所在的局部背景"，之后不再每轮改。
4. **固定冻结再评审的节奏。** 每天最多冻结一次，评审期间禁止推送。两份盲审的意见合并后按主题分批改，不再见一条否决修一条。只报盲审分，自评只留档。
5. **把模拟器能证明的和必须真机证明的分开。** 真机这条线需要：签名的 iOS 内测包（上传 TestFlight 要你批准）、1–2 台 Android 真机、一个受控的真实服务账号，再加 15 分钟真人用 VoiceOver/TalkBack 听一遍。
6. **目标分阶段。**
   - 第一阶段：两份盲审都达到 85 以上、没有否决。这是评分表自己的及格线，模拟器上能做到。
   - 没有真机时，现实上限大约 87–90。实施方估过 93，但没有任何独立评审支持。
   - 95 要在真机、签名、真实服务都齐了以后才谈得上，而且两个严格评审都打到 95，本身就很难。建议把 95 当作真机阶段的拉伸目标，不作为每轮的门槛。
