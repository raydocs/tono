# Tono：从“小项目后台”到“完整运营产品”的差距评审
> 基于仓库 `0c41d9f`：已读批准方案、指定文档、全部文案、页面结构与数据合同。只读，未调用生产接口；线上状态以你提供的 **2026-09-10** 为准。  
> 三项问题已用仓库代码在内存中复核：过期采集源仍可显示正常、静默请求返回 400、延迟告警没有留下待发送记录。
**结论：方向不需要推倒，但现在更像“运营信息浏览器”，还不是“运营工作台”。**  
五入口、统一词表、`Measured<T>`、持久事故、任务租约、审计都是值得保留的地基。真正缺的是：
**发现问题 → 决定怎么处理 → 执行 → 证明生效 → 告诉客户 → 留下账目与后续责任。**
节点切接口、资料编辑、客户投影回填、Windows 失败报告都属于已知交付项；下面重点评审它们完成以后仍然存在的缺口。
**优先级：P0＝立即补安全底线，未补前不依赖它值守或自动操作；P1＝随后两周打通日常流程；P2＝数据积累后再自动化。**
## 1. 怎样成为“每天早上打开的那个产品”
### 1.1 【P0】早上先回答“今天的信息可信吗”，再说“没有事故”
- **为什么：** `App.tsx` 把客户、事故、发布列表只加载一次；切换页面不会刷新。头部 `sourceStamp()` 只要求**任意一个源 ready**，并取最新时间，采集器过期也可能显示“数据源正常”。这会让运营者相信昨天的世界。[证据](services/ops-console/src/lib/use-fleet.ts#L47)
- **怎么做：** 今天页定时刷新，窗口重新获得焦点时补拉；显示“本页截至何时”，过期后撤下确定性结论。头部接真实 `system/health`，分别说明采集、判定、客户端覆盖、执行器是否可用；目录没改动不能等同于目录服务失效。
- **晨间流程：** 首屏按顺序呈现“昨夜发生并恢复了什么 → 现在需要处理什么 → 今天必须续费/回访什么”。无事故时也应有可行动的日报，而不是一句空白的平安。
- **验收：** 保持页面打开，制造一个隔离测试事故，不手动刷新也能看到；停止数据源后不能继续宣称正常。
### 1.2 【P0】出事先能叫醒你：建规则之前，要修通告警生命周期
- **为什么：** 当前 `planDeliveries()` 遇到尚未达到延迟的事故只执行 `deferred++`，**不保存待发记录**；判定引擎只在状态转换时产生事件。新事故等待 900 秒后若没有新转换，不会再次进入规划，严重事故可能始终不通知。不是“加一条规则”就完成了。[证据](services/control-plane/src/ops/alerts.ts#L247)
- **怎么做：** 开事故时持久化待发记录，设 `notBefore`；到期重新检查事故是否仍存在、是否静默、规则是否启用，再发送。提前恢复则取消待发并留下原因。规则上线时预览“已有哪些事故会被补发”。
- **单人默认策略：** 严重客户影响走即时通知；Canyon 这类尚未确认客户影响的劣化进入观察/摘要；到期和缺资料走每日待办，不全都半夜叫醒人。
- **验收：** 覆盖“持续超过延迟才发、延迟内恢复不发、发送失败重试、主通道不可达”的完整时序；“发送测试成功”只证明通道，不证明事故能触发通知。
### 1.3 【P0】处理事故要完成“止血与复测”，不能只完成“标记已处理”
- **为什么：** 今天页主动作是认领，认领后变成标记已处理；抽屉没有把诊断、节点动作和结果验证串起来。人工 `resolve` 直接改为 resolved，而界面把它显示成“已恢复”。**运营者点了按钮，不等于客户能用了。**[页面](services/ops-console/src/pages/Today.tsx#L175)、[处理器](services/control-plane/src/ops/handlers/incidents.ts#L291)
- **怎么做：** 每个事故给一张处置卡：已知事实、尚未确认的影响、推荐下一步、预计影响、复测条件、下次检查时间。将“人工结束跟进”和“技术验证恢复”分开记录；允许误报关闭，但必须选择原因，不能计入恢复成功。
- **Canyon 的具体处理：** 先核对联通回程 10% 的测量时间、样本量和连续性 → 查同一时间段联通客户的真实连接失败 → 重测相关路径 → 有客户影响才迁移相应客户 → 验证替代节点连接成功。不能仅凭这个数自动全节点下架，也不能说“10% 客户连不上”。
- **另一个立即修复项：** 前端静默传 `{seconds:14400}`，后端只接受 `until` 或 `durationSec`，实际会返回 400；统一请求合同并补真实处理器测试。[前端](services/ops-console/src/lib/api.ts#L175)、[后端](services/control-plane/src/ops/handlers/incidents.ts#L273)
### 1.4 【P0】客户来问时，后台应在一分钟内给出“可发送的答案”
- **为什么：** 客户详情四个关键动作全部禁用；诊断报告区域固定显示“还没有回传的诊断报告”。这些不会因为投影回填完成就自动可用。[证据](services/ops-console/src/pages/CustomerDetail.tsx#L79)
- **怎么做：** 客户详情先做“客服模式”：最近一次完整连接尝试、设备与版本、失败阶段、是否关联公共事故、可用替代路径、需要客户补充的唯一问题。按钮直接生成回复草稿，而不是要求运营者翻五个区块。
- **跟进闭环：** 记录“已回复／等客户验证／约定何时回访／已确认恢复”；客户第二次来问时能接续上次处理。先做轻量服务记录，不必上完整工单系统。
- **数据诚实：** 区分“正在回填、该版本不支持、客户未授权、没有发生、上报失败”。历史窗口没有保存的运营商信息，回填也补不回来，不能一直让人等。
### 1.5 【P1】把“开通了账号”推进到“客户第一次成功使用”
- **为什么：** 客户状态和连接投影主要覆盖已经能认证、能上报的人；下载失败、验证码失败、首次取目录失败的人，可能还没进入这些视图。最容易流失的人恰好不可见。
- **怎么做：** 建最小开通漏斗：授权/购买 → 登录 → 注册设备 → 取目录 → 首次握手 → 首次实际业务成功。未完成且超过约定时间进入回访待办；先接已有事件，不为漏斗增加全量浏览日志。
- **验收：** 新客户卡在任何一步，都能知道下一步是谁做、怎么联系、何时再看；不能把“无遥测”统一当离线。
### 1.6 【P1】待办必须能办结；月底必须能对账
- **为什么：** 今天页待办是前端临时推导出来的文字，没有对象链接、完成状态和凭证；同一客户的额度提醒在今天页是 90%，详情是 80%，到期窗口又分别是 14 天和 7 天，口径漂移已经重现。[今天页规则](services/ops-console/src/lib/chores.ts)、[详情规则](services/control-plane/src/ops/handlers/customers.ts#L174)
- **怎么做：** 待办统一由服务端产生，增加 `subjectId、dueAt、status、nextAction、completionEvidence`。续费待办进入账单页，回来登记“实际支付额、覆盖周期、新到期日”，验证资料更新后办结；缺资料进入对应编辑位置。
- **月底流程：** 锁定月份 → 汇总实收、退款/补偿 → 服务器、家宽、域名、控制面等成本归期 → 比较商家账单与计量 → 单独列出差异 → 导出月结。至少支持手工录入与 CSV，不必先接支付平台。
- **账目边界：** 年付机器要区分现金支出与月摊成本；金额记录币种、汇率日期、服务周期。当前 `CustomerBillingDto` 是套餐和额度，不是收入账本。用量缺测时显示“成本待核对”，不能算出漂亮的毛利。
### 1.7 【P1】新机器上架应是一张“可售验收单”
- **为什么：** 商家账号、五处登记、探针、目录是分散事实；全部有勾也不代表中国客户能用。现在 `identitySync` 的勾主要依据曾取过 roster，不是“目标身份版本已安装”的证明。[证据](services/control-plane/src/ops/handlers/nodes-data.ts#L349)
- **怎么做：** 登记购买与成本 → 配置部署 → 五处绑定核验 → 真实 Reality 握手与目标业务检查 → 大陆相关运营商验证 → 少量客户试用 → 正式上架。每步保留证据和失败退路；复用现有 provisioner，不另造任意 SSH 命令入口。
- **可售门槛：** 必须知道它适合谁、承载余量、成本、何时续费、谁替代它；缺关键验证时不能自动变成在售。资料编辑功能完成后，要接进这张验收单，而不是孤立表单。
### 1.8 【P0 安全门槛／P1 完整流程】旧机器下线要同时结束客户依赖、凭证和账单
- **为什么：** “下架”不等于已经没人连接，“退役”不等于商家停止扣钱。更直接的问题是：上下架按钮入队 `catalog_retire/catalog_relist`，其 executor 为 `worker`，当前调用链未见对应执行消费者；**部署 hub 不能补上这条链**。[任务定义](services/control-plane/src/ops/jobs.ts#L68)、[入队处理](services/control-plane/src/ops/handlers/nodes.ts#L271)
- **怎么做：** 立即按真实执行能力禁用未接通动作；随后实现“替代容量检查 → 停止新分配 → 发布目录 → 看客户端刷新与迁移确认 → 撤销旧凭证 → 商家取消续费/销毁确认 → 归档”。目录移除已有实现，但不能冒充全部步骤完成。
- **保护条件：** 未迁移客户单列，不能只看一刻的在线人数；保留撤销下架和迁移失败回退。疑似凭证泄露另走紧急吊销流程，不等待优雅排空。
- **验收：** 退役完成必须同时证明“客户不再依赖、旧入口不可继续用、后续账单已处理”。
### 1.9 【P0 文案真实性／P1 发布闭环】客户端发布必须对应真实更新源
- **为什么：** 文案承诺“发布后客户端会自动更新”，当前发布操作仅更新 `client_releases`；公开的 `appcast.xml`、`windows/latest.json` 仍由静态资产提供。登记成功不能证明更新源改变。[登记写入](services/control-plane/src/ops/releases.ts#L250)、[实际更新源](services/control-plane/src/index.ts#L4653)
- **怎么做：** 未联动前改成“登记发布状态”或禁用；接通后显示构建、校验、更新源发布、客户端实际收到、安装后健康五个阶段。撤回要区分停止分发与已安装客户端的恢复方案。
- **发布流程：** 内部设备 → 小批量 → 看连接失败/崩溃是否升高 → 扩大范围；异常暂停。Windows 失败报告可以独立发布，不必绑上全量日志默认开启等更大变更。
### 1.10 【P0】你关上电脑以后，系统也必须有人看守
- **为什么：** hub 单点已被方案接受，但死人开关仍由同一个控制面判定和发送；控制面自身不工作时，它不能给自己报死。VPN 故障时，通知与后台访问也可能一起受影响。
- **怎么做：** 用独立于 Tono 数据面的探测路径检查登录、目录、更新源和控制面心跳；至少一条通知通道在 VPN 不可用时仍可收取。高危事故未确认时升级提醒，恢复后补发摘要。
- **恢复流程：** 仓库已有备份与 preview 恢复脚本，下一步不是再写一份，而是验证“恢复后账号、目录、凭证、计量能工作”，记录实际恢复耗时。**不打开 `/ops2/` 不会停止新 cron、判定和其他服务端写入**，回滚手册必须包含这些开关。
## 2. 10 倍客户／3 倍节点时，哪些设计会坏掉
以下是静态代码中已经存在的触发点，不是泛泛的“以后要优化性能”。
| 优先级 | 会坏在哪里，为什么 | 怎么做 |
|---|---|---|
| **P0** | **第 51 个客户开始可能在后台消失。** 列表默认 50 条，`App.tsx` 只保留 `.items`，丢弃 `nextCursor/total`；搜索、计数、待办都基于这半张名单。事故列表同样如此，后端还先取最新 500 条再在内存过滤游标。[证据](services/ops-console/src/app/App.tsx#L31) | 接真实游标分页；全局计数、搜索与筛选在服务端完成；进行中事故和恢复历史分开查询。用 201 位客户及超过 500 条历史事故验证“无遗漏”，不能只压布局。 |
| **P1** | **请求成本按全体对象增长，而不是按当前页增长。** 客户列表先读全部用户，每人再查状态与服务，最后才截页；200 人约需 402 条查询，仅返回 50 人。新节点接口也逐节点查询多组事实。[客户查询](services/control-plane/src/ops/handlers/customers.ts#L103)、[节点查询](services/control-plane/src/ops/handlers/nodes.ts#L95) | 先在 SQL 限定当前页，再批量 JOIN/聚合；摘要走投影。ETag 在昂贵读取前判断。扩容前按方案自己的每请求查询预算验收，而非先换数据库。 |
| **P1** | **固定回填预算追不上故障突发与历史重建。** 每 5 分钟各处理 200 个窗口，理论上限 57,600 个/天，实际还受执行成本影响；日报主要重算昨日，长时间回填到更早日期也不会自动补齐旧日报。[证据](services/control-plane/src/ops/cron.ts#L180) | 实时处理与历史补齐分队列/预算；公开水位、最老积压、处理速率；按受影响日期重算聚合。`BackfillHealthDto` 已有，先让处理器不再固定返回 `null`。 |
| **P1** | **一个人的两台设备互相覆盖。** `ops_customer_status` 以用户为主键，后到窗口覆盖设备、节点、平台与版本；Mac 正常可能盖住 Windows 失败，“最低版本”也实际取最后上报版本。[证据](services/control-plane/src/ops/customers.ts#L189) | 先维护每设备当前状态，再按明确规则聚合客户；允许“一个客户，多台设备，多条连接”。客服与迁移都按设备执行，按客户去重统计影响。 |
| **P0** | **“唯一判定”仍未真正统一。** 客户读取处理器另算 `customerVerdict()`，不是直接消费事故引擎同一结论；它与引擎对成功后的失败判断不同。规模越大，越容易出现“客户正常但事故未恢复”。[读取判定](services/control-plane/src/ops/handlers/customers.ts#L51) | 把客户判定及原因落为权威投影；列表、详情、事故引用同一规则版本。补跨页面、跨时间的语义测试，不只测字段类型。 |
| **P1** | **运营商画像和成功率会被污染。** 入库的已知出口 ASN 集合为空，`edgeViaExit` 无法可靠标记；节点去程聚合又未排除此类上报。失败即报与窗口事件也没有统一尝试 ID，存在重复计算同一次失败的风险。[证据](services/control-plane/src/ops/ingest-hooks.ts#L50) | 加 `attemptId、networkContextId、uploadPath、attributionConfidence`；同一次尝试跨来源合并；不能识别运营商时保留未知。不能把上传时的网络直接当连接发生时的网络。 |
| **P1** | **“人数”和“30 天”已经有统计语义问题。** 采用率处理器累加各天人数；直连候选每段日志把 `users` 加一，`bytes_30d` 也是累加。一个重度用户可看起来像很多人，影响发布与分流决策。[采用率](services/control-plane/src/ops/handlers/releases.ts#L127)、[候选计数](services/control-plane/src/ops/traffic-parse.ts#L399) | 采用率明确“区间内每设备最后版本”，客户去重；候选按用户×域名×日聚合，滚动计算 30 天；日志解析以 segment ID 幂等。重复上传不得增加用户数或成本估算。 |
| **P1；变更任务启用前为 P0** | **任务租约不是“只执行一次”。** hub 批量领取后串行处理，长任务让后续短租约任务过期；结果回传失败可能触发重试。取消数据库里的 leased 任务也不等于远端命令停止。[执行循环](ops-panel/jobs.py#L899) | 按可执行槽位领取；每节点互斥、操作 ID 在执行端去重；执行前核对目标版本，执行后检查真实效果。区分“取消请求、确认停止、结果未知”，后者不得盲重试重启。 |
| **P1** | **节点名称同时承担身份。** 名字进入目录、事件、任务和资产绑定；三倍节点带来更多换 IP、搬机、改名，容易把历史切断或关联到错机。 | 现在增加不可变 `nodeId` 与别名表，展示名可改；区分逻辑节点、实际机器、部署实例。先让新接口携带 ID，不要求一次性迁完所有客户端。 |
| **P1** | **节点数量增长不等于冗余增长。** 同商家、同线路、同 hub、同家宽上游可能一起故障；按节点逐条展示会把一次共因故障变成几十个待处理对象。 | 登记故障域与依赖关系，支持事故归并、共享上游影响和备用容量检查；按故障域限制批量操作。先测 hub 队列与覆盖缺口，再决定是否加第二收集器。 |
## 3. 值得现在埋接口的 outside-the-box 做法
原则：**现在埋可追溯的输入、输出与回执，不等于现在就让 AI 自动改生产。** 以下均可留在现有五入口，不必再加导航。
| 优先级／做法 | 为什么值得 | 现在怎么埋，自动化边界是什么 |
|---|---|---|
| **P1：失败报告 → 客服回复草稿** | 最直接节省单人时间，也让失败即报立刻产生客户价值。 | `SupportCase` 关联 attempt、设备、事故、证据；输出“已确认/待确认、客户操作步骤、替代路径、回访时间”。草稿逐条可追到证据，运营者确认后发送；不让模型编造被墙原因或恢复承诺。 |
| **P1：续费前自动给节点更换建议** | 节点该不该续费，比 CPU 曲线更接近经营决策。 | `ReplacementProposal` 保存现机、候选、运营商表现、容量、故障域、月成本差、迁移成本与证据有效期；比较“续费／换 IP／换线路／退役”。先出建议单，不自动买机器。 |
| **P1：直连候选 → 可发布变更单** | 当前生成草案后要求复制粘贴，审批、签名和发布之间容易丢失上下文。[当前文案](services/ops-console/src/copy/settings.ts) | `PolicyChangeSet` 包含基线版本、域名 diff、冲突检测、影响范围、签名、灰度范围、回滚版本；批准后走既有发布路径。GeoIP 在大陆不等于应该直连，强制代理例外必须优先，不能省流量却暴露用户真实出口。 |
| **P1 埋接口／P2 自动推荐：后台判定反哺客户端** | 真正减少客服量的方法，是客户端先避开已知坏路径。 | 发布精简 `NodeAdvice`：稳定节点 ID、运营商/地区适用范围、建议权重、原因码、证据有效期、版本。客户端回传采用与连接结果；过期回退本地选择，保留手选，加入容量限制与随机分散，防止所有人涌向同一台。 |
| **P1：内部 SLO／客户服务报告** | 能回答“这月客户实际体验怎样”，也为续费解释和补偿提供依据。 | 按平台、运营商、节点记录真实连接成功率、连接耗时、已验证中断时长，以及**缺测时长与覆盖率**；保存统计口径版本和维护排除项。先做内部报告，不能上线一天就用机器在线率冒充客户 SLA。 |
| **P1：每周“最值得做的三件事”** | 单人真正稀缺的是注意力，不是图表。 | 汇总重复报修、即将耗尽、闲置高价机器、待续费线路、分流可节省流量，给出预计节省金额/时间、置信度和操作入口；不确定值明确标估算。每次执行后记录实际收益，校正建议。 |
| **P1：离线报修胶囊** | 故障最严重时，客户端可能根本传不上失败报告；“失败即报”天然有盲区。 | 本地保存有界、脱敏的诊断包和 attempt ID，恢复联网后补传，区分发生时间与收到时间；给客户一个报修码关联客服记录。补传旧故障不能被当成当前新事故。 |
| **P1：一次变更的效果回执** | 审计只说明谁按过按钮；运营者需要知道动作有没有救回客户。 | 统一 `ChangeReceipt` 关联事故、任务、目录/规则版本、执行前后证据、客户端确认、回退结果。下架、身份同步、发布、分流都复用；未来自动化必须拿到回执才能算成功。 |
## 4. 最大的三个风险
### 风险一【P0】：后台给出可信外观，却没有可信结论
**为什么：** 静态首屏、部分源正常即假绿、分页漏对象、客户判定分叉、重复失败与错误分母，都会制造“数字很精确但意思不对”。随后接节点推荐或自动下架，只会放大错误。
**怎么做：** 先验收时间、范围、样本、覆盖率、去重和规则版本；区分测量时间与判定时间；不确定性直接影响动作权限。以真实投诉回放证明“同一客户在所有页面解释一致”，而不是继续增加状态词。
### 风险二【P0】：会记录事故，但救不了事故；尝试救时又扩大影响
**为什么：** 延迟告警断链、静默字段不一致、上下架缺消费者、发布登记不等于实际分发，都是“纸面闭环”。同时运维逻辑与账号、计量共享控制面，后台故障可能越界影响客户核心路径。
**怎么做：** 能力门控、持久待发、真实执行消费者、执行端幂等、效果验证、回退必须成套；先开只读任务。补独立存活监测和服务端停用开关。验收单位从“一个按钮”改成“一次事故从发现到客户恢复”。
### 风险三【P0 原则／P1 落实】：完整产品化把隐私与最高权限集中到一个操作者手里
**为什么：** 批准方案的默认完整连接日志、按用户服务画像，再加节点操作权限，使后台成为高价值目标。邮箱遮罩只是展示偏好，不是权限隔离；访问审计与日志窗口虽已有地基，仍需证明实际有效。
**怎么做：** 建议重审“默认完整日志”的必要性：优先最小失败报告与客户端本地聚合；原始日志按目的授权、限定时间、到期回收。复用并验收现有读取窗口与审计，覆盖删除及备份恢复后的数据处理；将采集凭证与高危执行能力分权，保留离线恢复凭据，避免全部控制权只有一条路径。
## 建议的完成顺序
- **P0：先做到“不误导、不漏报、不假执行”。** 修新鲜度、分页、延迟告警、静默请求和能力门控；未接实际更新源的发布动作不得承诺自动更新。
- **P1：亲手走通四张单。** 一次事故处置单、一次客户回访单、一台机器上下线单、一份月结单；每张都必须有结果证据。
- **P2：再让建议自动执行。** 先积累“建议—操作—客户效果”的样本；不要把一个刚上线一天的判定系统直接升级成自动驾驶。
**最重要的产品验收问题只有一个：明天早上，你能否不靠记忆、不翻 SSH 和聊天记录，就知道今天该做什么，并在做完后确信客户真的好了？**
